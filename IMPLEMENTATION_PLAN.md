### Блокеры, найденные в интеграционной ветке (до слияния)

- **B-1. Миграции на чистой установке (подтверждено прогоном).** Базовые
  `db/0*.sql` уже содержат новую схему, но не записывают версии в
  `schema_migrations`; `tools/migrate.py` на свежей базе применяет 0001–0006 и
  падает на 0024 (`column q.on_critical_path does not exist` — колонка
  переименована в 0060, а 0024 пересоздаёт вид со старым именем). Шаг гейта
  `docker compose run --rm migrate` на свежей базе не проходит.
- **B-2. Устаревший `web/dist`.** Последняя сборка — `89f8147`; после неё 14
  коммитов меняли `web/src`. `run.sh` отдаёт старый фронт поверх нового API.
- **B-3. PostgreSQL-тесты никогда не запускались.** 13 тестов ключевых
  исправлений (атомарность, блокировка, инварианты, история) были skip. При
  первом запуске (волна 0) **8 из них падали** из-за фикстур, написанных до
  слияния веток (не из-за продукта); исправлено в `wave/0-ci`: общий помощник
  `tests/pg_support.py`, `confirm_complete=True` в тесте атомарности; один тест
  (миграция 0024 на новой схеме) помечен `xfail(strict)` до B-1.
- **B-4. Нумерация миграций по DA.** Следующая миграция с номером меньше 0062
  на существующей базе применится последней, а на чистой — раньше: порядок
  разъедется.
- **B-6. DA-05 откладывает все задачи в работе (найдено прогоном волны 0).**
  Любая роль задачи с потраченными часами и без ETC получает
  `remaining_unknown` и нулевой остаток (`db/migrations/0005_task_role_etc.sql`),
  задача уходит в перенос `ETC_REQUIRED` независимо от `смета − факт`. На выданном
  датасете (ETC нет) так отложены все 6 задач InProgress, включая **DB-202** —
  пример онбординга, который обязан растягиваться на 2+ спринта. Базовый план:
  5 из 37 в квартале (было 10), целиком 0 инициатив из 15 (было 2), PI
  Predictability — «не определён»; после факта спринта 1 в квартале 0 задач.
  Решение для волны 1: остаток = `смета − факт` как *предварительный* (задача
  планируется с пометкой «оценка не подтверждена», алерт `overrun`), а
  `ETC_REQUIRED` — только когда результат 0 у незакрытой задачи.
- **B-7. Дрейф схем «чистая установка» и «обновление миграциями».**
  `plan_assignments.work_hours`: NOT NULL + CHECK > 0 в базовой схеме против
  nullable без CHECK после миграций; разные имена CHECK-ограничений у
  `kpi_snapshots` и `task_actuals`. Находит `tools/schema_fingerprint.py`.
- **B-8. Демо-файлы и README.** Закоммиченные `demo/actuals_sprint_*.csv` в старом
  формате (нет `completed_sp`), загрузка через UI сохраняет их как черновик
  (DA-19) без пересчёта; полный отчёт требует явное число (в т. ч. 0) в каждой
  ячейке «задача × роль» с остатком, а шаблон отдаёт пустые ячейки. README §1.1,
  §4 описывают устаревший сценарий.
- **B-5. Безопасность не тронута.** S-1 (path traversal, `app/server.py:545`) и
  S-2 (запись без авторизации) в ветке остались.

## 2. Правила процесса (для каждого MR)

### 2.1. Ветки
- **Интеграция — долгоживущая `release/product`** (создана от
  `fix/audit-integration`, `8175300`). `develop` и `main` не трогаем, пока
  волна 7 не пройдёт полную проверку: `develop` остаётся стабильной версией,
  которую можно показывать и сдавать. `main` защищена — только MR.
- Одна волна = одна ветка `wave/N-кратко` от свежего `release/product`, внутри —
  атомарные коммиты по пунктам. Крупная волна может делиться на несколько MR
  (`wave/N-… → release/product`), каждый проходит CI самостоятельно.
- Релиз: один MR `release/product → develop`, затем `develop → main`.
- CI-файл нужен и на `develop` (волна 7 переносит его вместе с релизом; если
  `develop` придётся менять раньше — отдельный cherry-pick только `.gitlab-ci.yml`).
- В заголовке коммита — идентификатор пункта: `DA-27: …`, `S-1: …`, `NEW-02: …`,
  `B-1: …`. Так трекер и `git log --grep` сходятся.
- После слияния волны удалять её ветку; стопку `fix/da-*` удалить после
  волны 1, поставив тег `audit-fixes-2026-10-03` на `8175300`.
- Ветки и теги публикуются на `origin` только по явному решению владельца
  репозитория; локально ветки ведутся без `push`.

### 2.2. Миграции
- Номер — следующий по порядку (`0063`, `0064`, …), не номер пункта.
- Каждая миграция дублируется в базовых `db/0*.sql` (чистая установка) **и**
  проверяется CI-проверкой эквивалентности схем (см. 3.1).
- Миграции идемпотентны (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP … IF EXISTS`).
- Изменение замороженных контрактов (`02_contract.sql`, имена метрик ADR-018) —
  отдельный коммит с ADR и пометкой в MR.

### 2.3. Definition of Done (MR не сливается без этого)
1. CI зелёный: unit, PostgreSQL-интеграция, фронт, свежесть `web/dist`,
   эквивалентность схем.
2. Тест на каждый закрытый пункт (негативный сценарий, где он есть в
   `response_astra.md` §12).
3. `v_plan_violations` с `severity='error'` пуст на полном цикле
   (датасет → факт 1–6) — проверяет CI-джоба цикла.
4. **Документация обновлена по таблице 2.4** в том же MR.
5. `FIXES_TRACKER.md`: статус, коммит, отметка «документация».
6. Если изменились контрольные числа (задач в квартале, дефицит, BF) —
   перегенерирован отчёт DA-50, README ссылается на него, числа руками не
   вписываются.

## 3. Волны

Порядок выбран по зависимостям: сначала то, без чего нельзя проверять
остальное (CI), затем приём уже сделанной работы, затем безопасность, затем
открытые решения модели и новые фичи. Оценки — для одного разработчика.

### Волна 0 — инфраструктура проверки · ветка `wave/0-ci` → `release/product` · ~1 день
Цель: чтобы следующие MR проверялись машиной, а не глазами.
- `.gitlab-ci.yml` (репозиторий на GitLab codenrock):
  - `unit`: `uv run --group dev pytest`;
  - `pg`: сервис `postgres:17`, `TEST_DATABASE_URL`, запуск `*_postgres` тестов;
  - `cycle`: чистая база из `db/0*.sql` + seed → `tools/demo_cycle.py` →
    0 ошибок инвариантов в каждом прогоне;
  - `schema-equivalence`: база A = чистая установка, база B = старая база
    `develop` + `tools/migrate.py`; `pg_dump --schema-only` A и B совпадают;
  - `web`: `npm ci && npm run build`, затем `git diff --exit-code web/dist`;
  - `lint`: ruff (на первом шаге только новые ошибки).
- `CHANGELOG.md`, шаблон MR с чек-листом из 2.3.
- Документация: README §13 (как запускаются проверки), RUNBOOK (CI как гейт).
