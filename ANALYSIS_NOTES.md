# Анализ проекта PI-Planner (рабочий документ, 2026-10-03)

> Рабочие заметки для команды, не для сдачи. Приоритет — устройство проекта и
> его проблемы. Презентация и «продаваемость» — в конце и кратко.
> Источник: чтение кода (`app/`, `db/`, `etl/`, `web/src`, `docs/`), прогон
> `pytest` (102 passed). Docker-стек НЕ поднимался — цифры плана взяты из README/ADR.

---

## 0. Коротко

**Сильная сторона:** инженерно это один из самых зрелых хакатонных проектов,
какие можно представить: чистая функция планировщика, 31 независимый SQL-инвариант,
объяснение каждого решения, журнал фактов с воспроизводимым состоянием,
мониторинг, бэкапы, ADR.

**Главная слабость — содержательная, а не техническая:** на выданных данных
план берёт **10 из 37 задач**, а 26 переносит из-за «нет роли в штате»
(в основном «Руководитель проекта», 449 ЧЧ в 25 задачах). Формально это верно,
но на защите это выглядит как «сервис сказал, что ничего нельзя». Организаторы
разрешили **дообучение** (ответ №2) — и сценария «что будет, если дообучить
ENG-423 на РП» в продукте нет. Это самая дешёвая и самая сильная доработка.

**Вторая слабость — пересчёт (20% оценки) упрощён сильнее, чем кажется:**
velocity не обновляется по факту, перерасход часов делает задачу «почти готовой»,
SP задачи в работе списываются повторно целиком.

**Есть настоящая уязвимость:** path traversal в раздаче статики позволяет
прочитать любой файл контейнера, включая `/proc/self/environ` с паролем БД.

## 1. Баги и проблемы (по приоритету)

### P0 — исправить до сдачи

**1.1. Path traversal в статике** — `app/server.py:485`
`target = DIST / rel` не нормализуется, а `Path.is_relative_to` проверяет только
лексически. Проверено: `/../../app/db.py`, `/%2e%2e/%2e%2e/app/db.py` → `is_file()=True`,
`is_relative_to=True`. Запрос `curl --path-as-is https://host/%2e%2e/%2e%2e/%2e%2e/proc/self/environ`
вернёт окружение процесса (DSN с паролем). Если сервис публичный — его прочитает
любой, включая соседние команды.
Исправление (две строки):
```python
target = (DIST / rel).resolve()
if not target.is_file() or not target.is_relative_to(DIST.resolve()):
```

**1.2. Запись открыта всем** — `POST /api/dataset` стирает все прогоны и факт.
Если стенд для жюри публичный, любой посетитель (или конкурент) может
обнулить демо прямо перед проверкой. Минимум: токен в `.env`
(`PI_PLANNER_UPLOAD_TOKEN`), проверка заголовка в `do_POST`; или режим
read-only для публичного стенда + кнопка «сбросить демо» на свою машину.

**1.3. Выбранный прогон «залипает» после загрузки** — `web/src/hooks/useRun.tsx:39`
`selected` не сбрасывается после загрузки датасета или факта, а загрузка
датасета перезапускает `run_id` с 1 (`TRUNCATE … RESTART IDENTITY`), а
перезагрузка факта удаляет прогоны. Если пользователь вручную выбирал прогон,
после загрузки экраны покажут чужой или несуществующий прогон (пусто).
Это легко поймать на живом демо. Исправление: в `useRun` считать
`selected` валидным, только если он есть в `runs`; плюс `setRunId(null)` после
успешной загрузки (`DatasetDropzone.tsx:26`, `ActualsDropzone.tsx:59`).

**1.4. README обещает проверки факта, которых нет** — `app/ingest.py`
README §4: «дата вне спринта… отсутствующие колонки… проверяются». В коде нет
проверки, что `actual_start/actual_end` попадают в спринт, и что
`actual_end >= actual_start`. Критерий жюри прямо говорит: «сопоставить
объяснения команды с поведением сервиса». Либо добавить проверку
(5–10 строк в `load_actuals` рядом с `sprint_end`, `ingest.py:376`), либо
убрать фразу из README. Лучше добавить.

### P1 — качество пересчёта (20% оценки)

**1.5. Velocity не учится на факте.** `v_team_capacity_sp` (`db/04_views.sql:51`)
считает ёмкость только по `team_history` (по 2 снимка на команду). ТЗ:
«ресурс команды… по средней фактической производительности». После загрузки
факта спринта N логично добавлять выполненные SP в среднее. Сейчас команда,
которая провалила спринт, в пересчёте всё ещё планируется с прежней скоростью —
пересчёт оптимистичен ровно там, где должен предупреждать. Исправление: витрина
`v_team_velocity_actual` (SP задач, впервые Done в спринте, по команде) и
`UNION` с `team_history` в `v_team_capacity_sp`. Это заметное улучшение
«качества пересчёта» почти бесплатно, и его легко показать на слайде.

**1.6. Перерасход часов маскирует риск.** `app/planner.py:772` — если по
задаче потратили смету целиком (или больше), а она не Done, остаток = 0
(`GREATEST(…, 0)` в `v_task_remaining_hh`), и планировщик ставит
символические 0.01 ЧЧ и пишет «работа по смете фактически выполнена,
задача закрывается в спринте k». Т.е. **задача, которая буксует, прогнозируется
как закрытая в следующем спринте без ресурсов**. Демо-файлы (`demo/actuals_sprint_2/3.csv`
с часами `0.01`) это как раз обходят. Исправление: (а) колонка «остаток, ЧЧ»
(`remaining_estimate`) в шаблоне факта — переоценка от команды; (б) без неё —
правило «перерасход ⇒ остаток = X% сметы» + жёлтый алерт `overrun`.

**1.7. SP задачи в работе списываются повторно целиком.** README сам признаёт.
После факта спринта 1 задача, сделанная наполовину, снова съедает полный
`estimation_sp` из ёмкости команды начиная со спринта 2 — пересчёт пессимистичен
и может выталкивать другие задачи. Исправление: `remaining_sp = SP × remaining_hh / estimated_hh`
в `load_inputs`/`TaskInput` (одно место).

**1.8. Зависимости по умолчанию `start_start`.** `planner.py` / ADR-013:
`start(blocked) ≥ start(blocking) + 1`. Блокирующая растянута на 3 спринта —
зависимая стартует во втором, пока блокирующая ещё идёт. ADR честно пишет, что
на текущем сиде оба режима дают одинаковый план, но жюри по формулировке
«соблюдать зависимости» скорее ожидает finish→start. Раз результат одинаков —
переключить дефолт на `finish_start` бесплатно и снимает вопрос на защите.

**1.9. Неатомарность «данные + план».** `ingest.py:150` и `ingest.py:435–437`:
факт/датасет коммитятся одной транзакцией, план пишется другой. Если
планировщик упадёт — база уже с новым фактом, а «текущий» прогон старый.
Для демо редкость, но решается: при ошибке `run_plan` — компенсирующее удаление
загрузки или общий `with db.transaction()`.

### P2 — корректность метрик и интерпретации

**1.10. Bus Factor завышен из-за синонимов навыков.** Навыки режутся по запятым
и сравниваются по `lower()`. В датасете: `Kafka` / `Apache Kafka`,
`Microservices` / `Microservices Архитектура` / `Микросервисы`,
`Core Spring` / `Spring Core` / `Core`, `CI/CD` / `CI/CD (GitLab, Jenkins)` / `GitLab CI`,
`Регресс` / `Regression/Smoke/Functional testing` / `Функциональное тестирование`,
`REST API` / `REST/gRPC` / `REST/SOAP интеграции`. Итог «86 из 116 навыков с одним
носителем» частично артефакт. Жюри за Bus Factor даёт 15% и может это заметить.
Исправление: `SKILL_ALIASES` в `etl/config.py` по образцу `ROLE_ALIASES` (уже
есть механизм) — 15 строк словаря. Опционально — группы навыков (семейства).

**1.11. KPI Bus Factor всегда = 1.** `planner.py:1902`: минимум по навыкам почти
гарантированно 1 → показатель неинформативен и не меняется между прогонами.
Добавить рядом долю востребованных навыков с BF ≥ 2 (или число критичных) — это
число будет «двигаться» при дообучении/найме.

**1.12. «Выполнение плана спринта» = 100%, когда на спринт ничего не планировали.**
`planner.py:1880`. На штемпеле KPI это выглядит как успех. Лучше `null`/«—»
с подписью «нет плана на спринт».

**1.13. Две модели «SP в спринте».** Гант показывает доли SP по спринтам
(`plan_task_sp`), а say/do кладёт SP задачи целиком в спринт окончания
(`planner.py:1859`). Можно защитить («SP засчитываются по закрытию»), но это
надо явно сказать в README/на слайде, иначе цифры на двух экранах не сходятся.

**1.14. Знаменатель KPI «процент выполнения квартала» крошечный.** «Включена в
план» = все живые задачи инициативы в квартале. При 10/37 задачах в плане это
1–2 инициативы из 15 → KPI прыгает 0% ↔ 100%. Формула соответствует ТЗ, но на
слайде нужно показывать и знаменатель («1 из 1»), и частичные инициативы.

### P3 — мелочи и гигиена

- **Дрейф документации «7 спринтов / 525.71 ЧЧ».** ADR-025 вернул 6 спринтов,
  но старое осталось: `db/01_schema.sql` (DEFAULT `sprint_count 7`, COMMENT
  pi_periods/sprints), `db/04_views.sql` (комментарии `v_sprint_fund_factor`,
  `v_pi_fund_factor`, `v_satellite_capacity`, `v_role_supply_hh`),
  `app/views.py` (note у `sprints`, `v_sprint_fund_factor`, `v_pi_fund_factor`,
  `v_satellite_capacity`), `app/planner.py` (докстринги про 6.5714/525.71),
  `db/03_substitutions.sql` (rationale «525.71 ЧЧ»), `etl/config.py`
  (комментарий у `ETL_VERSION`). Жюри, открывшее код, увидит противоречие с README.
- `app/server.py:41` — докстринг «ни один маршрут не пишет в базу» устарел (есть POST).
- `app/server.py:288` — нечисловой `Content-Length` → `ValueError` → ответ 503
  «база недоступна». Должен быть 400.
- Фронт в docker-режиме советует «запустите run.sh» (`PlanScreen.tsx`) —
  нерелевантно для основного способа запуска.
- `PlanScreen.tsx`: «остальные перенесены на следующий PI» — часть из них
  «к отмене», формулировка неточна.
- Нет CI (ни `.github`, ни `.gitlab-ci.yml`): тесты и `tsc` никто не гоняет
  автоматически, хотя всё готово для одного workflow-файла.
- Нет линтера/типизации Python (ruff/mypy упоминаются только в .gitignore).
- Часы `0.01` в demo-CSV — утечка технического костыля в демо-данные.

## 2. Архитектура: оценка

### Надёжность — **высокая для демо, средняя для продакшена**
+ Детерминированный планировщик; `build_plan` — чистая функция, тестируется без БД.
+ 31 инвариант в SQL проверяет результат **независимо от кода алгоритма** — сильнейший
  аргумент корректности (30% оценки), его надо выносить на слайд.
+ Факт — неизменяемый журнал, состояние воспроизводится `apply_actuals()`; повторная
  загрузка спринта безопасна; валидация файла «всё или ничего».
+ Read-only сессии по умолчанию, белый список витрин, параметризованный SQL.
− Path traversal (1.1), запись без авторизации (1.2), неатомарность (1.9).
− Соединение к БД на каждый запрос, без пула; `load_inputs` — ~15 отдельных
  соединений без общего снимка (сейчас спасает `WRITE_LOCK`).
− Тесты проверяют SQL «по тексту» через fake-DB; живые витрины и инварианты
  проверяются только вручную (RUNBOOK). Нет интеграционного теста «датасет →
  план → 0 ошибок инвариантов» в CI.

### Модульность — **хорошая по слоям, тяжёлая внутри**
+ Чёткие слои: ETL → нормализованное ядро → витрины → планировщик → контракт →
  API-белый список → фронт по хуку на витрину.
+ Параметры модели в данных и конфиге (focus factor, часы, алиасы ролей, режимы).
− `app/planner.py` — 2100 строк, `build_plan` ≈ 500 строк с замыканиями. Логично
  разрезать: `funds.py` (фонд), `placement.py` (размещение), `explain.py`
  (причины), `alerts.py`, `kpi.py`.
− Бизнес-логика в двух местах: часть в SQL (Bus Factor, дефицит, отклонения,
  diff), часть в Python (KPI, алерты). Это осознанно, но повышает риск
  расхождений — уже видно по пункту 1.13.

### Масштабируемость — **рассчитана на одну организацию и один квартал**
− Один PI жёстко: `pi_periods … LIMIT 1` и `v_pi_fund_factor LIMIT 1` (≈15 мест).
  Второй квартал без переделки не добавить.
− Загрузка датасета = `TRUNCATE` всего: нет мульти-тенантности и истории кварталов.
− `WRITE_LOCK` — процессный; два инстанса `app` будут гоняться (нужен
  `pg_advisory_lock`).
− `v_plan_diff` и `v_engineer_absence_risk` — `CROSS JOIN` по всем прогонам с
  коррелированными подзапросами; CTE `base` материализуется целиком. На десятках
  прогонов норм, на тысячах — медленно.
− ETL привязан к раскладке одного Excel-листа (маркеры блоков — хорошо, но
  формат всё равно уникальный). Для другого бизнеса нужен импорт из Jira/CSV.
+ Алгоритм жадный, O(задачи × спринты × инженеры) — на сотнях задач быстро.

### Сложность развёртывания — **низкая для пользователя, высокая «под капотом»**
+ `cp .env.example .env && docker compose up -d --build` — одна команда.
+ Запасной `run.sh`/`run.bat` без Docker; собранный `web/dist` в git.
− 8 сервисов (db, app, bootstrap, migrate, backup, caddy, prometheus, grafana)
  для сервиса на 45 задач — избыточно для демо: дольше старт, больше точек отказа,
  самоподписанный сертификат пугает жюри. Стоит иметь профиль «lite»
  (db + app на http://localhost:8000) как дефолт для проверки, а мониторинг —
  `--profile ops`.

### Презентабельность (UI) — **хорошая, но главная мысль не вынесена наверх**
+ 7 экранов, звёздная карта своим SVG с детерминированной раскладкой, Гант на
  CSS-grid, причины в панели задачи, прогноз/факт разделены, адаптив, a11y.
− Вывод «бэклог упирается в отсутствующие роли» живёт в README §9, а не на
  первом экране. Нужен блок-сводка на «Плане»: «10 из 37 в квартале. 26 ждут
  роль “Руководитель проекта”. Дообучение ENG-423 → +N задач».

## 3. Желательные фичи (по соотношению ценность/цена)

1. **What-if «дообучение/найм»** (самое важное). Таблица `role_substitutions` и
   `efficiency` уже есть. Сценарный прогон (не трогает базовую линию):
   «ENG-423 дообучен на РП с эффективностью 1.3», «нанят 1С-разработчик с
   спринта 3». В UI — сравнение «как есть / со сценарием» по задачам и KPI.
   Легально по ответу №2 и превращает слабость данных в главный «вау».
2. **Velocity из факта** (п. 1.5) — прямо бьёт в критерий пересчёта.
3. **Колонка «остаток» в факте + алерт перерасхода** (п. 1.6).
4. **Синонимы навыков** (п. 1.10) — точнее Bus Factor.
5. **Сводка-«светофор» на главном экране**: что в квартале, что под угрозой,
   почему, что сделать (нанять / дообучить / пересогласовать).
6. Экспорт CSV плана и рисков (ТЗ не требует, но удобно для отчёта жюри).
7. CI-workflow: pytest + tsc + (опц.) интеграционный прогон инвариантов в
   контейнере Postgres.

## 4. Перспективы и подача (кратко, без увлечения)

**Как объяснить ценность за 30 секунд:** «Сервис отвечает руководителю не
“сколько задач влезет”, а “почему не влезет и что сделать”: какую роль нанять,
кого дообучить, какая цель квартала под угрозой после спринта N. Каждое решение
объяснено и проверено 31 независимым правилом».

**Ключевые тезисы для слайдов:**
- корректность доказуема: инварианты, 0 ошибок на каждом прогоне;
- объяснимость: у каждой задачи фраза «почему» + разбор по ролям и людям;
- пересчёт без потери обещания: базовая линия неизменна, прогноз ≠ факт;
- инсайт по данным: узкое место — не скорость команд и не зависимости, а
  отсутствующие роли; 5 из 8 незаменимых — вокруг Team-Platform;
- (после фичи 1) «одно дообучение → +N задач в квартал».

**Продаваемость другому бизнесу:** идея универсальна (ресурсное планирование с
ролями + bus factor), но сейчас продукт привязан к одному Excel-формату, одному
кварталу и одной организации, без авторизации. Для жюри достаточно сказать,
что путь к продукту — импорт из Jira/YouTrack, мульти-квартал и роли доступа;
архитектура (витрины + контракт планировщика) это допускает.

**Риск на защите:** документации очень много (README 46 КБ + 9 документов ~4 тыс.
строк с историей ревью). Жюри это не прочитает; стоит иметь одностраничный
«путь проверяющего»: запуск → 3 клика → где смотреть причины, риски, Bus Factor.

## 6.2. Делать в урезанном виде

- **DA-01 стек задачи.** Требование реальное (PDF «В»), но связи «задача →
  навык» в датасете нет. Ручная разметка 45 задач = выдуманные данные, которые
  жюри не сверит с Excel, и она ещё сильнее сузит и так пустой план.
  Урезанно: в README/на слайде явно — «в датасете стек выражен ролью сметы»;
  в коде — проверка «у исполнителя есть базовый стек роли» (словарь
  роль → ключевые навыки) и признак в причине решения. Полную модель
  `task × role × skill` не строить.
- **DA-04 «есть замена».** Полный сценарий отсутствия не делать; дёшево —
  учитывать свободные часы второго человека той же роли в `v_engineer_absence_risk`.
- **DA-33 оранжевый алерт.** Добавить задачи `in_quarter`, которые могли
  стартовать в следующем спринте, но уехали из-за роли. Полный пересмотр
  горизонтов — нет.
- **DA-39 дефицит против фонда всего PI.** После факта сравнивать с фондом
  оставшихся спринтов — одна поправка в `v_role_deficit`/`v_role_coverage_org`.
- **DA-40 атомарность.** Без версий и «промежуточной публикации»:
  при падении `run_plan` откатить загрузку (компенсация) или общая транзакция.
- **DA-27 velocity.** Аудит прав: базовую формулу ×0.8 не менять. Но добавить
  факт спринтов в среднее для пересчётов (мой п.1.5) — соответствует ТЗ
  («средняя фактическая производительность»); базовая линия от этого не меняется.
- **DA-51 тесты.** Один интеграционный сценарий на временной PostgreSQL в CI
  (датасет → план → факт 1–3 → 0 ошибок), а не вся программа из §12.
- **DA-08 парттаймер 40+40.** Реально, но касается 4 человек и замороженного
  PK. Сначала замерить, меняет ли это план на датасете; если нет — описать как
  ограничение.
