# Как работает PI-Planner: алгоритмы и принципы

Это обзорный документ: он объясняет, **как система думает**, простыми словами и
со ссылками на код. Точные правила — в [PLANNER_SPEC.md](PLANNER_SPEC.md),
причины решений — в [DECISIONS.md](DECISIONS.md) (ADR-номера ниже), схема данных —
в [SCHEMA.md](SCHEMA.md), эксплуатация — в [RUNBOOK.md](RUNBOOK.md).

Если код и документ расходятся, прав код: правьте документ.

## 1. Общая картина

```
 Excel-датасет                                         факт спринта (CSV/XLSX)
      │                                                         │
      ▼                                                         ▼
  etl/load.py ──► seed.sql ──► PostgreSQL ◄── app/ingest.py (проверка, журнал загрузок)
 (нормализация,    (ядро:      │   │
  DQ-находки)       задачи,    │   └─► витрины db/04_views.sql (v_*): готовые ответы
                    люди,      │          на вопросы «сколько часов», «кто заменит» …
                    орбиты)    │
                               ▼
                 app/planner: load_inputs() ─► build_plan() ─► write_plan()
                 (только чтение)  (чистая функция)   (одна транзакция + приёмка)
                               │
                               ▼
        контракт: plan_runs, plan_task_schedule, plan_assignments, plan_task_sp,
        task_state, alerts, kpi_snapshots, plan_baseline …
                               │
                               ▼
        витрины + API (app/server.py, app/views.py) ─► веб-интерфейс (web/)
```

Идея в одном предложении: **ядро данных хранит факты, витрины отвечают на
типовые вопросы, планировщик — чистая функция «вход → план», а всё, что видит
пользователь, читается из записанного плана и витрин**.

## 2. Принципы

1. **Чистая функция в центре.** `build_plan()` не обращается к базе: всё нужное
   лежит во `Inputs`. Поэтому план воспроизводим и проверяется юнит-тестами без
   PostgreSQL (`tests/test_planner.py`). Чтение — `load_inputs()` (сессия
   read-only), запись — `write_plan()`.
2. **Одна транзакция на прогон.** Частично записанного плана не бывает. Прогон
   пишется со статусом `failed`, затем проверяется приёмкой (инвариантами,
   `db/05_invariants.sql`) и публикуется, только если ошибок (`severity=error`)
   нет. Иначе остаётся для диагностики (`PlanValidationError`).
3. **Витрины — контракт чтения.** Планировщик читает только `v_*` и таблицы
   контракта, не «ядро изнутри». Один источник правды на понятие: фонд часов —
   `v_sprint_fund_factor`, остаток работ — `v_task_remaining_hh`, пара «инженер ×
   роль» — `v_engineer_role_coverage` (ADR-012).
4. **Детерминизм.** Любая ничья разрешается стабильно (по топологии и `task_id`,
   по `engineer_id`). Один и тот же вход всегда даёт один и тот же план.
5. **Объяснимость.** У каждого решения есть код и текст причины (в том числе у
   «включено»), а прогон записывает в `plan_runs.params` режимы, версию формул,
   календарь, хэши исходного Excel и ёмкость команд. Любой результат можно
   объяснить без повторного расчёта.
6. **Честная неопределённость.** Нет данных — значит «неизвестно», а не ноль:
   остаток работ без ETC, стек без разметки, KPI без обещанного знаменателя
   (`N/A` с `calculation_status`). Приближения помечаются явно.
7. **Прогноз и факт — разные строки.** `kpi_snapshots.kind` различает
   `forecast` и `actual`; промежуточный факт не сравнивается с итоговой нормой.
8. **Права на запись узкие.** Соединение с базой по умолчанию read-only;
   пишут только явные `execute(read_only=False)` и `transaction()`. Загрузки идут
   под одной блокировкой записи (сервер многопоточный).
9. **Планировщик не обещает оптимума.** Алгоритм жадный; «перенесено» значит
   «не влезло при уже принятых решениях», а не «невозможно» (ADR-011, ADR-015).

## 3. Модель данных, которую использует план

| Понятие | Что это | Откуда |
|---|---|---|
| PI | квартал из шести двухнедельных спринтов (14 дней, ADR-025) | `pi_periods`, `sprints` |
| Ядро | команда | `teams` |
| Спутник | инженер; роль, грейд и стек принадлежат ему | `engineers`, `engineer_skills` |
| Орбита | привязка инженера к команде со своей ставкой; у совместителей их две | `engineer_orbits` |
| Фонд часов | `ставка × 80 ЧЧ × множитель спринта`; полная ставка даёт 480 ЧЧ за PI | `v_sprint_fund_factor`, `v_satellite_capacity` |
| Ёмкость команды в SP | `средняя velocity × focus_factor (0,8)` | `v_team_capacity_sp` |
| Остаток работ | по задаче и роли: ETC главнее, иначе смета минус факт | `v_task_remaining_hh` |
| Инициатива | группа задач (`prodf_id`), у неё приоритет `priority_rung` | `initiatives` |

**Орбиты и займы (ADR-001).** Инженер сначала тратит бюджет своей орбиты. Если
свою задачу в спринте закрывать нечем, остаток бюджета можно отдать другой
команде — это **заём**. Заём разрешён только при свободной ёмкости и всегда
отмечается в назначении (`is_loan` считает СУБД). Сумма всех орбит человека не
может превысить его общий фонд.

**Роли не заменяются (ADR-010, ответ организаторов №2).** Исполнителя берут
только из родных строк `v_engineer_role_coverage`. Замещение — возможность на
уровне схемы (ADR-009), но в штатном плане отклонено; выход из дефицита —
наём или дообучение.

**SP и часы — два разных бюджета.** Универсального перевода SP в часы нет.
Часы — фонд людей, SP — пропускная способность команды. Планировщик
расходует оба вместе (§4.4).

## 4. Алгоритм планировщика

Версия алгоритма — `greedy-priority-topo@2`, формулы — `FORMULA_VERSION`
(`app/planner/constants.py`). Пакет `app/planner/`:

| Модуль | Роль в алгоритме |
|---|---|
| `loading.py`, `queries.py` | читают вход из витрин |
| `graph.py` | пересчитывает живые границы зависимостей |
| `capacity.py` | ёмкость команд в SP на момент прогона |
| `priority.py` | порядок обхода задач |
| `funds.py` | фонд часов/SP, размещение задачи по спринтам и людям |
| `core.py` | `build_plan()`: проходы, причины, симуляция следующего PI |
| `alerts.py`, `kpi.py` | алерты и KPI поверх готового плана |
| `writer.py` | запись контракта и приёмка |

### 4.1. Подготовка входа

1. **Живой граф зависимостей** (`_refresh_live_graph`). Для каждой незавершённой
   задачи нижняя граница старта `earliest_start_sprint` пересчитывается заново:
   по живым блокирующим — рекурсивно (`граница блокирующей + зазор`), по уже
   завершённым — по **фактической дате события**. Будущая фактическая дата не
   разблокирует задачу в старом срезе прогона. Граница пишется в
   `plan_dependency_bounds` и проверяется инвариантом.
2. **Ёмкость команд** (`effective_capacity`, ADR-030). Базовый прогон
   (`as_of_sprint = 0`) берёт `v_team_capacity_sp` без изменений. Пересчёт на
   спринт `k` добавляет наблюдения закрытых спринтов `1..k−1`: среднее
   считается по всем наблюдениям поровну, затем умножается на `focus_factor`.
   Будущий факт не используется.
3. **Кандидаты на роль.** Для каждой пары «задача × роль» — инженеры с этой
   ролью из покрытия, у которых есть **все** подтверждённые требования к
   навыкам. Нет разметки — требований нет, но прогон помечает стек как
   `unverified`: отсутствие требований не доказывает совпадение стека.
4. **Порядок обхода** (`order_tasks`, ADR-032). Очередь — по убыванию приоритета,
   ничья — по топологии и `task_id`. Приоритет: явный бизнес-приоритет
   инициативы главнее всего; иначе по стратегии `max` (по умолчанию: MAX(rung) по
   задачам инициативы), `task`, `weighted` (взвешенно по SP) или
   `completion_first` (при равенстве раньше та инициатива, которую дешевле
   закончить).

### 4.2. Нижняя граница старта

Для задачи берётся максимум из: первого открытого спринта (`max(1, as_of_sprint)`
— закрытые спринты не пишутся), границы живого графа и зазоров от уже
поставленных блокирующих. Режим зависимостей:

* `finish_start` (по умолчанию, ADR-028): `старт(блокируемой) ≥ конец(блокирующей) + зазор`;
* `start_start`: `старт(блокируемой) ≥ старт(блокирующей) + зазор`.

### 4.3. Размещение одной задачи (`_allocate_task`)

Для кандидата-спринта `s`, начиная с нижней границы:

1. **Бюджет работы по SP.** Свободные SP команды в спринте `free_s` ограничивают
   работу задачи: `суммарная работа по ролям ≤ ΣЧасовРоли × free_s / SP_задачи`.
   Нет свободных SP — спринт пропускается.
2. **Роли закрываются параллельно и независимо.** По каждой роли перебираются
   кандидаты: сначала свои орбиты (по убыванию свободных часов, предпочитая
   прежних исполнителей задачи), затем заёмщики. Исполнитель берёт столько часов,
   сколько позволяют остаток бюджета спринта и свободный фонд. Часы
   списываются с орбит человека, **своё ядро первым**.
3. **Растягивание.** Что не поместилось в спринт, переезжает в следующий: окно
   задачи — от первого до последнего спринта с работой. Разрывы допустимы, но
   подсвечиваются предупреждением `WINDOW_HAS_GAP`.
4. **Эффективность.** Часы исполнителя = часы работы × `efficiency` (сейчас везде
   1,00). `plan_assignments.hours` — часы человека, а не эквивалент сметы.
5. **Откат.** Если до конца квартала часы не нашлись, все пробные списания
   возвращаются в фонд, задача уйдёт в перенос.
6. **Доли SP** (`_sp_shares`, ADR-029). После размещения часов доля SP спринта
   пропорциональна выполненной в нём работе: `SP × работа_s / ΣРабота`.
   Округление вниз до сотой, недостающие сотые раздаются по наибольшим
   остаткам и только туда, где у команды ещё есть место; иначе кандидат
   отвергается, задача пробует более поздний спринт. Сумма долей равна SP к
   планированию (инвариант `SP_SHARES_MISMATCH`). Следствие: задача, у которой SP
   больше ёмкости спринта, растягивается минимум на два спринта.

Задача, у которой остаток неизвестен (`remaining_unknown`) или нечего
выполнять, не размещается и получает причину `ETC_REQUIRED`.

### 4.4. Проходы

| Проход | Что делает |
|---|---|
| 1 | Обход в порядке очереди; каждая задача — в минимальный подходящий спринт. Режим `greedy`: задачи решаются по отдельности, частичная инициатива допустима. Режим `atomic`: пробная упаковка инициативы целиком; не влезла хоть одна — откат всей инициативы |
| 2 | Перенесённая блокирующая тянет за собой зависимые (`propagate_deferrals`) |
| 3 | Догон зазоров (`fix_gaps`): если блокирующая уехала позже, зависимая переставляется или переносится |
| 4 | Повторная упаковка: переносы проходов 2–3 вернули часы и SP в фонд, перенесённые задачи пробуют встать снова; повторяется до стабилизации |

Если квартал закрыт (факт загружен за последний спринт), все задачи получают
`PI_CLOSED`.

### 4.5. Причины решений (ADR-022, ADR-031)

Причина строится по журналу **той же проверки**, что размещает задачу, а не
придумывается отдельно:

| Код | Смысл |
|---|---|
| `PLANNED` | включена; текст говорит, кто и почему (в том числе источник приоритета) |
| `ROLE_NOT_IN_STAFF` | в штате нет ни одного человека с нужной ролью |
| `SKILL_UNAVAILABLE` | роль есть, но нет инженера с подтверждённым стеком |
| `BLOCKED_BY_DEFERRED` | блокирующая задача сама не вошла |
| `GRAPH_HORIZON` | самый ранний старт по зависимостям — за пределами квартала |
| `TEAM_SP_EXHAUSTED` | часов хватает, ёмкости SP команды нет |
| `ROLE_HOURS_EXHAUSTED` | не удалось разместить X из Y часов роли |
| `INITIATIVE_ATOMIC` | режим `atomic`: инициатива не влезла целиком |
| `ETC_REQUIRED` | остаток работ неизвестен |
| `PI_CLOSED` | квартал закончился |

Конкуренты за ресурс называются поимённо с местом в очереди; фраза «выше в
очереди» говорится только о тех, кто действительно выше. В колонке
`decision_reason` для совместимости дублируется старый код (`M2` — нет
ресурсов, `M3` — не готовы смежные команды).

**Решение об отмене планировщик не принимает.** Он выдаёт только `in_quarter` и
`deferred_next_pi`. Значение `cancelled` в схеме и интерфейсе зарезервировано
под рекомендацию, которую заказчик подтверждает отдельно (§6).

### 4.6. Пробный следующий PI

Для задач, перенесённых из-за нехватки часов или ёмкости (и зависимых от них),
считается сценарий: тот же штат и календарь, пустой следующий квартал. Он
показывает прогнозную дату завершения и объясняет, почему задача не влезла:
из-за конкуренции (отдельно помещается) или сама по себе не помещается («нужно
пересмотреть объём, декомпозицию или ресурс»). Это сценарий, а не доказательство
невыполнимости. Симуляция идёт только в режиме `greedy`.

### 4.7. Сборка и запись

После проходов `_assemble` добавляет: алерты (§7), KPI (§8), `plan_baseline` (только
для `as_of_sprint = 0`), слепок `task_state` всех задач, статистику
(`in_quarter`, `deferred`, `loan_hh`, число целых и частичных инициатив),
оценку стабильности исполнителей и полный блок `params`. `write_plan()` пишет
всё одной транзакцией и запускает приёмку (§12).

### 4.8. Пересчёт по факту

Раз в спринт загружается отчёт о факте (`app/ingest.py`). Правила:

* отчёт **закрывает спринт**, только если в нём есть строка каждой активной
  задачи и числа часов либо явный `0` по каждой роли с остатком; пустая ячейка —
  «нет данных». `draft` и `incomplete` сохраняются, но состояние не меняют;
* исключения факта (новая роль, перерасход, часы у `ToDo`, возврат статуса) не
  отбрасываются, а сохраняются с причиной в `actual_report_issues`; новую роль и
  перерасход нужно подтвердить ETC — это вызывает новый прогон;
* состояние задач **воспроизводится** из исходного набора и закрытых отчётов, а не
  накапливается правками; при исправлении отчёта он и все более поздние
  заменяются (прежние версии файлов хранятся в `upload_revisions`, ADR-034);
* после этого запускается прогон с `as_of_sprint = N + 1`: закрытые спринты не
  переписываются.

## 5. Доступность, квалификации и стабильность

* **Доступность инженера по спринтам** (ADR-033) меняет его орбитальные ставки
  в нужных спринтах (`app/availability.py`) и переписывает фонд.
* **Квалификации** (`app/qualifications.py`) — датированные подтверждённые
  навыки человека; они описывают людей и **не дают права** замещать роль.
* **Разметка стека задач** (`app/skill_review.py`) — подтверждённые требования
  «задача × роль × навык»; после сохранения план пересчитывается.
* **Стабильность исполнителей.** Для продолжающейся задачи планировщик
  предпочитает прежнего исполнителя, если у него есть фонд и навыки. Смены и их
  причины (`unavailable_or_unqualified`, `task_deferred`,
  `capacity_or_competition`) пишутся в `plan_runs.params.stability`.

## 6. Цель и бизнес-результат

Техническое `Done`, предложение плана и подтверждённый результат — **три разных
факта** (`v_plan_goal_outcome`). Рекомендация отмены остаётся рекомендацией, пока
заказчик её не подтвердит. Цель инициативы достигнута, только если каждая её
задача с целевым этапом получила подтверждение `ACHIEVED` не ниже этого этапа.
Подтверждение (`confirm_task_goal`) пересчитывает план.

## 7. Алерты

Три типа из ТЗ, формируются в `app/planner/alerts.py`:

| Уровень | Тип | Когда |
|---|---|---|
| orange | `role_deficit` | независимый от расписания спрос готовых задач на ближайший спринт больше фонда роли; вклад каждой задачи ограничен одним полным фондом инженера за спринт; вердикт «НАЙМ» |
| red | `deadline_miss` | у инициативы есть задачи вне квартала; если инициатива была обещана в Неделе 0, цель «под угрозой»; дата указывается только если её даёт сценарий следующего PI |
| yellow | `cascade_shift` | задача закончится позже базового плана и тянет за собой зависимых; причина: `own_slip`, `dependency` или `capacity` |

## 8. KPI

Считаются в `app/planner/kpi.py` по формулам ТЗ (ADR-023); нормы хранятся в
`KPI_TARGETS` и приходят в строке KPI как `target_min` / `target_max`.

| KPI | Формула | Норма |
|---|---|---|
| Процент выполнения квартального плана (`pi_predictability`) | инициативы, завершённые за 12 недель / инициативы, **целиком** включённые в первоначальный план × 100% | 80–100% |
| Выполнение плана спринта (`say_do_ratio`) | фактически выполненные SP / первоначально запланированные SP × 100%; запланировано в спринт = SP задач, которые базовый план закрывает в этом спринте | 90–105% |
| Bus Factor (`bus_factor`) | минимум носителей по компетенциям, чья роль нужна бэклогу | не ниже 2 |

Важные детали:

* **Базовый план** — первый канонический прогон `as_of_sprint = 0`; пересчёты его
  не меняют.
* **Охват.** Рядом с процентом всегда показывается знаменатель мира:
  «обещано N из M, частично K, не обещано L». 100% на малом охвате — не успех.
* **Промежуточный факт.** До конца квартала факт сравнивается не с нормой
  80–100%, а с плановым накоплением: сколько обещанных инициатив база велит
  закрыть к концу спринта (`ahead` / `on_plan` / `behind`).
* **План завершений и бюджет работ** — разные числа: первое — SP задач,
  заканчивающихся в спринте по базе, второе — доли SP, которые тратит текущий план.
  Для закрытых спринтов точность прогноза сравнивается в
  `v_sprint_forecast_accuracy`.
* Нет знаменателя — `N/A` и `calculation_status` (`no_commitment`, `no_plan`,
  `no_relevant_skills`).

## 9. Bus Factor и звёздная карта

* **По ролям** (`v_bus_factor`): сколько инженеров на роль, включая роли без
  единого человека в штате — это вопрос найма.
* **По компетенциям** (`v_bus_factor_skill`, ADR-024): сколько инженеров владеют
  навыком. Спрос на навык берётся из подтверждённой разметки задач
  (`confirmed`), а для неразмеченных задач — оценка через роль, помеченная как
  приближение (`role_proxy`). Градация: «нет носителей» → «критично»
  (единственный носитель требуемого навыка, даже если коллеги по роли им не
  владеют) → «предварительно» → «единственный носитель» → «два» → «ок».
* **Риск отсутствия** (`v_engineer_absence_risk`): для каждой роли инженера в
  каждом спринте ищется альтернатива **той же роли** со свободным фондом того же
  спринта и всеми требуемыми навыками. Нет альтернативы по подтверждённому стеку —
  «нет прямой замены», стек не размечен — «замена не подтверждена».
* **Сценарий отсутствия** (`app/absence.py`, `GET /api/scenarios/absence`):
  инженер убирается из входа текущего прогона, план перестраивается без
  публикации; ответ — затронутые задачи и цепочки, потерянные инициативы,
  дополнительные перенесённые часы.

На карте размер точки — грейд, цвет — уровень риска, ромб — совместитель на двух
орбитах. Карту строит детерминированная раскладка без физики
(`web/src/screens/starmap/layout.ts`): одни и те же данные дают одну картинку.

## 10. Сценарии и аналитика качества

Все — read-only, ничего не публикуют, доступны только для текущего прогона и
перепроверяют, что план не обновился во время расчёта.

| Сценарий | Что делает |
|---|---|
| Чувствительность (`app/sensitivity.py`) | три детерминированных ухудшения входа: доступность инженеров −20%, остаток часов +20%, скорость команд −20%; вероятности не оцениваются |
| Кадровые меры (`app/workforce.py`) | сравнение найма (+0,5 ставки с лагом в один спринт), обучения (наставник теряет 0,1 ставки на учебный спринт) и перевода 0,5 ставки; меры ранжируются по числу «возвращённых» инициатив, прибавке SP и тому, насколько раньше закончатся задачи |
| Качество плана (`app/plan_quality.py`) | подтверждённая ценность, частичные инициативы, ожидание зависимостей, перенос обещанного, внеплановое завершённое, неиспользованный фонд дефицитных ролей, смены исполнителей |
| Сравнение режимов | `greedy` и `atomic` на одном входе; для малых входов (до 5 инициатив и 10 задач) — полный перебор порядков инициатив. Это точный ответ только среди перебранных порядков и этого алгоритма размещения, а не доказательство оптимума |

## 11. Качество данных и приёмка

* **ETL** (`etl/load.py`): блоки листа ищутся по маркерам, а не по номерам строк;
  текст нормализуется; навыки режутся по запятым **верхнего** уровня (запятая в
  скобках — часть навыка); роли и навыки приводятся к канону (ADR-006).
  Находки пишутся в `dq_issues`: `error` блокирует загрузку, остальные — материал
  для вопросов заказчику. Для каждого значения хранится координата ячейки Excel
  (`source_provenance`), так что решение прослеживается до исходного файла
  (`GET /api/tasks/trace`, `app/trace.py`).
* **Трудозатраты** — истина в сумме столбца матрицы сметы (ADR-002); расхождения
  трёх источников попадают в `plan_runs.params.estimate_conflicts`.
* **Приёмка плана** — `db/05_invariants.sql`, витрина `v_plan_violations`.
  Среди проверок: `SP_OVERFLOW`, `SP_SHARES_MISMATCH`, перегрузка инженера и
  орбиты, зазоры зависимостей, `START_BEFORE_EARLIEST`, назначения только в
  открытых спринтах, полнота `task_state`, наличие причины у каждого решения,
  непротиворечивость базовой линии. Перечень кодов и SQL смотрите в самой
  витрине: она — источник истины.

## 12. Контексты, доступ и наблюдаемость

* **Контексты PI и сценариев** (`app/contexts.py`): каждый набор
  данных живёт в отдельной схеме PostgreSQL; реестр — `public.pi_contexts`.
  Выбор — заголовки `X-PI-ID` и `X-Scenario-ID`.
* **Доступ** (`app/auth.py`, ADR-027): токен `Authorization: Bearer`, в базе
  только SHA-256. Роли `viewer` < `planner` < `admin`: просмотр; загрузка факта
  и подтверждения; загрузка датасета и журнал действий. Действия пишутся в
  `audit_log`. Неудачные попытки ограничивает `FailureLimiter`.
* **Витрины для фронта** (`app/views.py`, ADR-019): один маршрут
  `GET /api/views/{view}`, имя витрины и `ORDER BY` — только из белого списка,
  значение параметра в текст SQL не попадает.
* **Метрики** (`app/metrics.py`): Prometheus-формат, имена и метки — контракт с
  devops (`docs/OBSERVABILITY.md`); `route` берётся из фиксированного набора.

## 13. Ограничения и честные оговорки

* Алгоритм жадный: решение не оптимально в общем случае; `deferred_next_pi` — не
  приговор. Цену выбора показывают счётчики целых и частичных инициатив и
  сравнение режимов.
* Критический путь с длительностями и резервами не считается: `on_longest_edge_chain`
  — длина цепочки по рёбрам на момент импорта.
* Часы по роли не доказывают нагрузку конкретного инженера: факт приходит в
  разрезе роли.
* Для неразмеченных задач совпадение стека не доказано; Bus Factor по ним —
  приближение через роль.
* Сценарии «следующий PI», чувствительность и кадровые меры — гипотезы при том
  же штате и календаре, а не прогноз вероятности.
* Точные числовые отчёты получаются командой `python tools/current_report.py`
  после загрузки базы; копировать цифры из старых отчётов нельзя.
