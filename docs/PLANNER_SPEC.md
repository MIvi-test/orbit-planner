# Действующая спецификация PI Planner

Эта страница описывает правила текущего кода. История решений находится в
[DECISIONS.md](DECISIONS.md), прежняя редакция — в
[архиве](archive/PLANNER_SPEC_before_DA50.md). Формулы прогона фиксируются в
`plan_runs.params.formula_version`; входной Excel и версия ETL — в `load_batches`.
Контрольные числа получаются командой `python tools/current_report.py` после
загрузки базы, а не копированием старого отчёта.

## 1. Календарь и вход

Исходный PI-2026-Q3 начинается **01.07.2026** и состоит из **шести спринтов по 14 дней**.
Последний день PI — **22.09.2026**. Оставшиеся дни календарного квартала в план
не входят. Фонд полной ставки: **80 ЧЧ за спринт, 480 ЧЧ за PI**. Фонд по
команде и инженеру берётся из `v_sprint_fund_factor`, `v_pi_fund_factor` и
`v_satellite_capacity`; константу 480 нельзя применять к частичной ставке.

Новый PI или сценарий создаётся загрузкой Excel через «Новый PI или сценарий».
Дата начала задаётся при создании; продолжительность остаётся шесть спринтов.
Каждая пара `pi_id` / `scenario_id` имеет отдельную схему PostgreSQL с собственными
задачами, фондом, фактами, прогонами и KPI. Реестр `public.pi_contexts` хранит
имя схемы и SHA256 текущего датасета. UI отправляет выбранную пару в заголовках
`X-PI-ID` и `X-Scenario-ID`; сервер выбирает схему до чтения и записи данных.
Команда `tools/current_report.py --pi-id PI-2027-Q1 --scenario-id main`
строит отчёт для выбранного набора.

ETL хранит 45 задач, включая завершённые. Планируются текущие `ToDo` и
`InProgress`. Для каждой роли
задачи используется `v_task_remaining_hh`: исходная матрица сметы, накопленный
факт и последний подтверждённый ETC. Если часы исчерпаны, а ETC не указан,
остаток помечен неизвестным и задачу нельзя объявить выполнимой. Сумма часов
разных ролей корректно отражает **трудозатраты задачи**; она не равна
календарной длительности параллельной работы.

Находки качества исходных данных доступны построчно в `v_dq_issue_worklist`.
Решения о принятии, исправлении или повторном открытии добавляются в
`dq_issue_reviews`; исходная находка не меняется. Интерфейс позволяет
фильтровать список по правилу, уровню, объекту и состоянию. Для ошибок
показывается блокирующий статус до подтверждённого исправления.

## 2. Приоритет и упаковка

Очередь: `initiatives.priority_rung` по убыванию, внутри инициативы —
`task_sequence.topo_order`. По умолчанию `initiative_mode=greedy`: часть задач
инициативы может войти в PI. `atomic` доступен отдельным режимом. Метод
жадный и не доказывает глобальную оптимальность; `deferred_next_pi` означает,
что задача не вошла при уже принятых назначениях.

На экране рисков `GET /api/scenarios/sensitivity` пересчитывает текущий прогон
для трёх прозрачных изменений входа: доступность инженеров −20%, остаток часов
по ролям +20% и скорость команд −20%. Каждый результат сравнивается с
пересчитанным базовым планом на том же входе. Это детерминированные сценарии;
вероятность срыва по двум точкам истории команд не оценивается.

Инженер закрывает свою роль; замещения ролей отклонены организаторами.
Часы инженера ограничены ставкой и орбитами. Заём между командами допускается
только при свободной ёмкости орбиты и явно отмечается в назначении. Если для
задачи и роли подтверждены требования к навыкам, кандидат обязан покрыть их;
неразмеченные требования выводятся как неподтверждённые, а не как доказанное
совпадение стека.

При пересчёте для продолжающейся задачи прежний исполнитель получает
приоритет среди подходящих кандидатов со свободным фондом. Прогон сохраняет
в `params.stability` число сохранённых и изменённых связок «задача × роль»,
затронутых людей и причину каждой смены; экран плана показывает эту цену
пересчёта.

`GET /api/scenarios/workforce` ранжирует для выбранной роли, команды и даты
три типа гипотез: наём 0,5 ставки с лагом в один спринт, обучение с переводом
0,5 ставки сотрудника на новую роль и затратой 0,1 ставки наставника в учебном
спринте, а также перевод 0,5 ставки текущего носителя роли из другой команды.
Выигрыш измеряется восстановленными инициативами, чистым SP и ранним
завершением. Навыки нового или обученного сотрудника являются явно указанным
допущением сценария; штатное запрещённое замещение ролей не включается.

## 3. SP и часы

SP — отдельный бюджет пропускной способности команды. Часы инженеров
раскладываются по ролям и спринтам, затем остаток SP раскладывается по свободной
ёмкости команды от фактического старта. Универсального перевода SP в часы нет.
Задача может занимать спринт только по одному из этих бюджетов: в
`v_plan_task_progress` и карточке видны оба потока и причина длительности.
Результат достигается после последнего спринта с часами **или** SP.

`plan_task_sp` хранит доли SP по спринтам; их сумма равна `remaining_sp` из
`task_state`. `SP_OVERFLOW` проверяет бюджет команды в каждом спринте, а
`SP_SHARES_MISMATCH` — сумму долей. Фактические часы не уменьшают SP: для этого
нужно явное `completed_sp` в отчёте.

## 4. Зависимости и исторический план

Режим `start_start` требует `start(blocked) >= start(blocking) + gap`, режим
`finish_start` — `start(blocked) >= end(blocking) + gap`. Живой граф и
фактические даты завершённых блокирующих пересчитываются на момент каждого
прогона. Допустимая нижняя граница записывается в `plan_dependency_bounds` и
проверяется инвариантом `START_BEFORE_EARLIEST`. Будущая фактическая дата не
разблокирует задачу в старом срезе. `task_sequence.on_longest_edge_chain` —
длина цепочки по числу рёбер **на момент импорта**, а не критический путь с
длительностями и резервами.

`run_id` определяет расписание, назначения, доли SP, `task_state`, ролевой
остаток, граф и KPI. Историческая карточка читает снимки прогона. Справочные
экраны с текущим бэклогом, составом и навыками помечаются как текущие.
`v_sprint_deviation` для старого прогона ограничивается уже существовавшими к
его созданию закрытыми отчётами того же PI.

## 5. Факт и принятие результата

Загрузка отчёта не закрывает спринт сама по себе. `POST /api/actuals?sprint=N`
с `confirm_complete=true` закрывает его только при наличии строки каждой
активной задачи и числа часов либо явного `0` по каждой роли с остатком.
Пустая ячейка — отсутствие данных. `draft` и `incomplete` сохраняются, но не
меняют состояние задач, не запускают пересчёт и не создают фактический KPI.
При исправлении отчёта этот и все более поздние отчёты и прогоны заменяются,
после чего состояние воспроизводится из seed и закрытых отчётов.

Исключения факта (новая роль, перерасход, часы у `ToDo` или после `Done`,
возврат статуса назад) сохраняются с указанной причиной в
`actual_report_issues`. Часы по роли не доказывают нагрузку конкретного
инженера. Новую роль или перерасход требуется подтвердить ETC; ревизия
`task_role_etc` вызывает новый прогон.

Решение `cancelled` в расписании — **рекомендация**, не отмена заказчиком.
`v_plan_goal_outcome` отдельно показывает исходную цель R1–R6, предложенный
результат квартала и подтверждённый бизнес результат. Техническое `Done` без
подтверждения остаётся `unconfirmed_done`. Цель инициативы в
`v_initiative_goal_progress` достигнута только если каждая задача с целевым
этапом получила подтверждение `ACHIEVED` не ниже этого этапа.

## 6. KPI и версии формул

| KPI | Знаменатель | Числитель | Неопределённость |
|---|---|---|---|
| `pi_predictability` | Инициативы, целиком обещанные в каноническом прогоне Недели 0 | Инициативы, завершённые в пределах PI | Нет обещанных инициатив → `N/A` |
| `say_do_ratio` | SP, обещанные первоначальным планом на спринт | SP, подтверждённые фактом завершения в этом спринте события | Нет обещанных SP → `N/A` |
| `bus_factor` | Навыки, требуемые живым бэклогом | Минимальное число носителей критичного навыка | Нет релевантных навыков → `N/A` |

`kpi_snapshots.kind` различает `forecast` и `actual`, а
`calculation_status` объясняет `N/A`. Фактический KPI не публикуется по
неполному отчёту. Для навыков без разметки требований задачи используется
явно помеченное приближение через роль. Канонический baseline — первый
опубликованный прогон `as_of_sprint=0`; его `plan_baseline` не меняется.
`formula_version`, сценарий и календарь сохраняются в `plan_runs.params`.
`source_sha256`, `config_sha256` и версия ETL также фиксируются в прогоне.
Карточка задачи открывает `GET /api/tasks/trace`: решение, ролевой остаток,
фонд назначенной орбиты и исходные ячейки Excel с нормализованными значениями.
Если прежняя загрузка удалена, API явно сообщает, что исходные ячейки больше
не доступны; снимок прогона и его причины остаются.

`GET /api/plan-quality` собирает для текущего прогона подтверждённую ценность,
частичные инициативы, ожидание нижней границы зависимостей, перенос обещанного,
внеплановые SP, смены исполнителей и свободный фонд дефицитных ролей. Значения
считаются по опубликованному плану и принятому факту; исторический прогон
остаётся доступен в основных витринах, а анализ текущих потерь не выдаётся за
его снимок.

## 7. Приёмка плана

Источник истины — `db/05_invariants.sql`, витрина `v_plan_violations`.
`severity=error` отменяет публикацию рабочего плана; предупреждения видны в
интерфейсе. Проверяются, в частности: фонд инженера с учётом всех орбит,
SP команды и доли задачи, наличие требуемой роли и подтверждённого стека,
зазоры зависимостей, граница живого графа из `plan_dependency_bounds`,
назначения только в открытых спринтах, полнота `task_state`, причины каждого
решения и непротиворечивость baseline. Перечень кодов и точный SQL следует
читать в самой витрине; старые числовые замеры в RUNBOOK и REVIEW_RESPONSE
не являются критерием приёмки новой ревизии.
