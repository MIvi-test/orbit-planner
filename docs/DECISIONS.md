# Архитектурные решения (ADR)

Здесь записаны действующие решения: что выбрали, почему, **как поменять** и чем
за это платим. Точные правила планировщика — в [PLANNER_SPEC.md](PLANNER_SPEC.md),
обзор алгоритмов — в [ALGORITHMS.md](ALGORITHMS.md). Нумерация сохранена, потому
что на ADR ссылаются код, SQL и другие документы; решение, которое заменено более
поздним, оставлено короткой отсылкой.

Датасет-источник: один лист Excel с шестью таблицами подряд
(`Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx`). Действующие правила
предметной области описаны здесь и в [PLANNER_SPEC.md](PLANNER_SPEC.md).

## ADR-000. Нормализованное ядро вместо Data Vault

**Решение.** Нормализованное 3NF-ядро (около 20 таблиц) плюс вьюхи-витрины.

**Почему.** В домене Data Vault развернулся бы в 7 хабов, 7 линков и около 10
саттелитов, а любой рабочий запрос — в 6-way join с оконной фильтрацией по
`load_dts`. Причин брать Data Vault нет: источник один (лист Excel), схема
зафиксирована постановкой задачи, объём — меньше тысячи строк.

**Чем платим.** При интеграции с Jira, HR и таймшитами ядро придётся переносить в
Data Vault. На текущем объёме это оправданный размен.

## ADR-001. Часы на общих орбитах: «орбита с приоритетом»

**Контекст.** Модель «команда-ядро и инженеры-спутники». Часть инженеров висит на
двух орбитах по 0,5 ставки.

**Решение.** Спутник сначала обслуживает свои ядра по `capacity_rate`.
Невыбранный остаток доступен другим ядрам как **заём**.

**Почему.** При жёсткой привязке план нерешаем: непокрытый дефицит сосредоточен в
связках «ядро × роль», где роли в команде нет вообще (`v_role_deficit`). Свободный
общий пул решает задачу, но стирает оргструктуру. Заём сохраняет обе вещи.

**Как поменять.** Политика живёт в планировщике, схема её только фиксирует:
`plan_assignments.home_team_id` (чья орбита) против `serving_team_id` (чья задача),
`is_loan` считает СУБД. Жёсткая политика — запретить строки с `is_loan = true`.

**Следствие.** Оранжевый алерт `role_deficit` и метрика «кто у кого занимал»
считаются одним запросом, без дополнительных таблиц.

## ADR-002. Трудозатраты: истина — сумма столбца матрицы сметы

**Контекст.** В датасете три источника часов, и они расходятся у части задач.

**Решение.** `tasks.estimated_hh_effective` — сумма ненулевых ячеек столбца матрицы
сметы. Два других источника хранятся рядом (`estimated_hh_declared`,
`estimated_hh_matrix_total`), все расхождения попадают в `dq_issues` с кодом
`ESTIMATE_SOURCES_DISAGREE`.

**Почему.** Только это число раскладывается по ролям и людям, а именно его
потребляет планировщик. Иначе сумма потребностей по ролям не сходилась бы с
потребностью по задаче.

**Смена источника.** Требует согласованного распределения часов по ролям и
изменения планировщика. Пустая ролевая смета при ненулевой оценке блокирует
загрузку.

## ADR-003. Зависимости: канон «A блокирует B», зазор 1 спринт

**Контекст.** Связи бывают трёх типов: `has to be done before`, `is required for`,
`depends on`. Последний семантически читается в обратную сторону относительно
заголовков колонок.

**Решение.** Все рёбра канонизированы как «A блокирует B» по заголовкам
`blocking_task_id` и `blocked_task_id`. Исходный тип сохранён в `raw_type`. Зазор —
1 спринт.

**Почему.** Проверка по смыслу задач показала, что колонка A везде предшествует B:
заголовки не врут.

**Как поменять.** `etl/config.py` → `MIN_GAP_SPRINTS`.

**Для планировщика.** Живых рёбер немного, цепочки короткие. Зависимости — не
главное ограничение; настоящее — ресурсы (ADR-001), поэтому усилия вложены в
приоритизацию под ресурсным лимитом, а не в топологический solver.

## ADR-004. Базовая линия Недели 0 строится системой

**Контекст.** KPI предсказуемости и выполнения плана спринта требуют знать, что
было запланировано на Неделе 0. Исходная колонка «будет включено в спринт»
заполнена лишь у задач в статусе `Done`.

**Решение.** Исходная колонка сохранена как `tasks.committed_week0` для
трассировки, но для KPI **не используется**. Базовая линия фиксируется таблицей
`plan_baseline` в прогоне с `plan_runs.as_of_sprint = 0` и дальше не меняется.

**Почему.** Иначе знаменатель обоих KPI вырожден.

**Как поменять.** При датасете с заполненной колонкой заполнять `plan_baseline`
прямо из `tasks.committed_week0`.

## ADR-005. Приоритет инициативы = MAX(rung) её задач

**Решение.** `initiatives.priority_rung = MAX(rung)` по задачам инициативы.
Это приоритет по умолчанию; явный бизнес-приоритет и другие стратегии — ADR-032.

**Почему.** Приоритет инициативы определяется самой приоритетной работой в её
составе.

**Как поменять.** `etl/config.py` → `RUNG_AGGREGATION` ∈ `max | min | sp_weighted`.
Все неоднородные случаи лежат в `dq_issues` (`RUNG_NOT_UNIFORM`).

## ADR-006. Нормализация ролей и навыков

**Решение.** Канон ролей — строки матрицы сметы; разночтения приводятся к нему по
`etl/config.py → ROLE_ALIASES` (например, `Девопс` → `ДевОпс`,
`Разработчик IOS` → `Разработчик iOS`, `Разработчик BigData` →
`Разработчик Big Data`). Часы слитых строк суммируются. Таблица `role_aliases`
показывает, что именно слито.

Справочник ролей — строки матрицы **плюс** роли из профилей инженеров: отсутствие
спроса на роль в бэклоге не делает профиль ошибочным. Роль из профиля без строки в
смете получает `role_id` после сметных и находку `ROLE_WITHOUT_ESTIMATE` (info);
если это разнописание сметной роли — добавляют алиас. Пустая роль — `error`
(`ENGINEER_ROLE_EMPTY`), конфликт роли и грейда у совместителя — `error`
(`PARTTIME_ATTRS_DIFFER`); оба блокируют загрузку. Дополнительные квалификации
(дообучение) хранятся отдельно от основной должности и не означают замещения роли.

**Навыки.** `skills_declared` режется по запятым **верхнего** уровня (запятая в
скобках — часть навыка), ключ — `lower()` без лишних пробелов; дубли
совместителей схлопываются.

**Ограничение.** Если стек записан неоднозначно (например, `Java, Core, Spring Core`
вместо `Java Core`), навык режется наивно. Нужен точный матчинг — чинить здесь.

## ADR-007. Начало PI — начало календарного квартала

**Решение.** PI начинается в начале календарного квартала (ответ заказчика №5).
Длительность PI задаёт ADR-025: шесть спринтов по 14 дней.

**Как поменять.** `etl/config.py` → `PI_START`, `PI_END`, `SPRINT_COUNT`,
`SPRINT_LENGTH_DAYS`. Таблица `sprints` генерируется ETL целиком, длина спринта —
генерируемая колонка `sprints.length_days`. Guard в `etl.load.build_sprints()`
падает, если сумма длин спринтов не равна длине PI: ошибка конфигурации не доезжает
до витрин.

## ADR-008. Историзация только там, где она окупается

**Решение.** Два разных саттелита:

* **структурный** — `engineer_orbits` (кто вокруг какого ядра вращается), в
  пределах квартала статичен;
* **временно́й** — `task_state` (что с задачей было на каждый пересчёт), insert-only,
  PK `(run_id, task_id, as_of_sprint)`.

Остальное — инженеры, навыки, роли, инициативы, смета — в пределах квартала не
меняется и историзации не требует.

**Почему.** Полный SCD2 по всем измерениям стоил бы кратно дороже. `plan_runs` и
`task_state` закрывают и «откат на спринт назад», и оба KPI.

## Особенности данных, которые видны в находках качества

Полный журнал — `v_dq_summary` и экран «Данные».

| Код | Что это |
|---|---|
| `ESTIMATE_SOURCES_DISAGREE` | три источника часов расходятся (ADR-002) |
| `RUNG_NOT_UNIFORM` | неоднородный скоринг внутри инициативы (ADR-005) |
| `ROLE_ALIAS_APPLIED` | роль инженера приведена к канону (ADR-006) |
| `ROLE_ALIAS_MERGED` | две строки матрицы слиты в одну роль (ADR-006) |
| `DEP_VIOLATED_IN_SOURCE` | блокирующая задача ещё в работе, а блокируемая уже `Done` |
| `TRUNCATED_REF_VALUE` | значение справочника обрезано в исходнике |
| `TEAM_WITHOUT_HISTORY` (error) | у команды нет истории velocity: загрузка блокируется |
| `TEAM_HISTORY_STALE`, `TEAM_HISTORY_THIN` | история старше 90 дней до PI или меньше трёх точек |

Не попадает в находки, но стоит знать: опечатки в тексте справочников не мешают
загрузке (сопоставление идёт по числовому префиксу); в нумерации инициатив бывают
пропуски; `task_sequence.on_longest_edge_chain` — длина цепочки по рёбрам на момент
импорта, а не критический путь, и различает слабо.

## ADR-009. Взаимозаменяемость ролей — возможность на уровне схемы

**Решение.** Таблица `role_substitutions`: кто какую роль может закрыть, не ниже
какого грейда, с каким коэффициентом. Планировщик вправе её использовать: это вход,
а не поведение. Сейчас все строки имеют статус `rejected` (ADR-010).

**Три уровня нехватки лечатся по-разному:**

| Уровень | Механизм | Витрина |
|---|---|---|
| Человек есть, но в другой команде | заём (ADR-001) | `v_role_deficit` |
| Роли нет, но есть кому замещать | `role_substitutions` | `v_role_deficit_effective` |
| Закрыть некем нигде | наём | `v_role_coverage_org` |

**Как поменять.** Правила — `db/03_substitutions.sql`, вручную, ETL их не трогает.
Включить механизм = поменять статус в файле и перезалить его: витрины
(`v_engineer_role_coverage`, `v_role_coverage_org`, `v_role_deficit_effective`)
перестроятся сами.

**Обязательное следствие.** Замещение должно быть видимым:
`v_plan_assignment_detail.is_substitution` показывает, что инженер работает не по
своей роли.

## ADR-010. Замещения ролей отклонены: только дообучение

**Решение по предметной области.**
Замещать роли нельзя, человека можно только **дообучить**. Все строки
`role_substitutions` имеют статус `rejected`; планировщик читает
`v_engineer_role_coverage`, а она отфильтровывает `status = 'rejected'`, поэтому
решение не потребовало кода: только данные.

**Цена.** План сжимается: роли, на которые в штате нет людей, закрыть нечем.
Задачи по ним переносятся в следующий PI, на экране «Риски» — оранжевый алерт с
вердиктом «НАЙМ» (ответ №3: не подменять сеньором другой роли, показать риск и
перенести). Этот результат — ожидаемое поведение, а не перестраховка.

**Как поменять.** Один файл: `db/03_substitutions.sql`, заменить `'rejected'` на
`'confirmed'` и перезалить.

## ADR-011. Алгоритм планировщика: жадный приоритет и топология, не MILP

**Контекст.** Классический выбор — MILP (CP-SAT, OR-Tools) и оптимум. Здесь это
лишнее: узкое место не граф, а ресурсы, а вход маленький.

**Решение.** Жадный алгоритм (`app/planner/`, ядро — `core.build_plan`):
инициативы по приоритету, внутри — по `topo_order`; для каждой задачи ищется
минимальный спринт, где хватает SP команды и часов исполнителей; часы можно
растягивать на следующие спринты; не влезла — `deferred_next_pi` с причиной
(ADR-022).

**Почему.** Решение детерминировано и объяснимо: видно, почему каждая задача стоит
в своём спринте. MILP добавил бы зависимость (OR-Tools) и необъяснимый оптимум, а
заказчику нужен не «оптимальный» план, а понятный.

**Как поменять.** Алгоритм изолирован тремя функциями: `load_inputs()` → чистая
`build_plan()` → `write_plan()`. Замена — новая `build_plan()`; контракт и
`v_plan_violations` не меняются, версия алгоритма видна в `plan_runs.algorithm`.
Тесты — `tests/test_planner.py`, базы они не требуют.

## ADR-012. Пара «инженер × роль» — только из `v_engineer_role_coverage`

**Решение.** `by_role` (кто может закрыть роль) строится из `Inputs.coverage`, а он
заполняется из `v_engineer_role_coverage` вместе с `efficiency`. Страховка: если
инженера в вьюхе нет, его родная роль добавляется с `efficiency = 1`: человек не
может молча выпасть из плана.

**Почему.** Вьюха — единственный источник правды о паре «инженер × роль». Пока все
замещения `rejected`, она отдаёт родные пары; при включении дообучения или
замещения менять код не придётся.

**Как поменять.** Запрос `COVERAGE_SQL` и строка в `build_plan`. Тест —
`test_candidates_come_from_the_coverage_view`.

## ADR-013. Семантика зависимостей и атомарность инициатив

**Решение.**

1. `dependency_mode` — явный параметр прогона:
   * `finish_start` (**по умолчанию**, ADR-028): `start(blocked) ≥ end(blocking) + gap`;
   * `start_start`: `start(blocked) ≥ start(blocking) + gap`.
   Режим пишется в `plan_runs.params.dependency_mode`; независимая приёмка
   проверяет окно предшественника по этому же режиму.
2. Перенесённая блокирующая тянет зависимую за собой, и это проверяет инвариант
   `DEPENDENCY_BLOCKER_DEFERRED`, а не только код.
3. `initiative_mode`:
   * `greedy` (**по умолчанию**) — частичная инициатива допустима;
   * `atomic` — пробная упаковка инициативы целиком с откатом
     (`release_initiative` возвращает в фонд SP и часы всех её задач).

**Почему `greedy` по умолчанию.** «Всё или ничего» отнимает у плана задачи и не
добавляет пунктов KPI: показатель и так считает только полностью закрытые
инициативы. Какой режим нужен бизнесу — вопрос к заказчику, поэтому оба доступны.
Сравнение режимов на одном входе — экран «KPI», блок «Качество и потери плана».

**Как поменять.** `--dependency-mode` и `--initiative-mode` у `tools/run_planner.py`
или аргументы `build_plan()`.

## ADR-014. Пересчёт в середине квартала

**Решение.**

1. **Прошлое неприкосновенно.** `replan_floor = max(1, as_of_sprint)`: при
   пересчёте на начало спринта `k` планируются спринты `k..6`. Проверка
   `ASSIGNMENT_IN_CLOSED_SPRINT` ловит нарушение независимо от алгоритма.
2. **Прогон аддитивен.** Пересчёт — новый `run_id`; старые расписания остаются
   историей. `plan_baseline` пишется один раз, только при `as_of_sprint = 0`.
3. **Факт по ролям** берётся из `v_task_remaining_hh`, а не из `tasks.spent_time` и
   не из `task_state`.
4. **`task_state` — витрина, а не источник.** Проверка следит за полнотой слепка и
   правильным `as_of_sprint`.
5. **Ёмкость** — полные бюджеты спринтов от `as_of_sprint` до конца квартала.

**Ограничение.** Фактических часов по спринтам в датасете нет: `task_role_spent` —
итог по задаче и роли. Часы, уже потраченные в текущем спринте, не вычитаются.

**Как поменять.** `tools/run_planner.py --as-of-sprint k`; правило — `replan_floor`
в `build_plan`.

## ADR-015. Целевая функция, механика часов и орбиты назначения

**Решение.**

1. **Цель — лексикографическая**, без перестановок:
   `priority_rung DESC → topo_order ASC → start_sprint ASC`. Строка цели и
   пояснение («жадный отказ ≠ невыполнимость») едут в `params.objective` и
   `params.objective_note`, счётчики `initiatives_complete` и
   `initiatives_partial` показывают цену выбора.
2. **Механика часов:** роли внутри спринта закрываются параллельно и независимо;
   одну роль в спринте могут закрывать несколько человек; часы роли, не
   поместившиеся в спринт, переезжают в следующий; окно задачи — `[min, max]`
   фактически использованных спринтов, разрывы допустимы и видны как warning
   `WINDOW_HAS_GAP`; при неудаче все пробные списания откатываются (`funds.free`).
3. **Одна орбита на строку.** `_spend_from` сначала использует орбиту задачи, затем
   другие орбиты человека. `home_team_id` входит в PK назначения: несколько строк
   одного инженера на одной задаче и роли в одном спринте сохраняют источник часов
   каждой орбиты.
4. **Порядок кандидатов:** свои орбиты первыми (по убыванию свободных часов
   орбиты), затем заёмщики (по убыванию общего остатка), при равенстве — по
   `engineer_id`.
5. **Бюджет орбиты — жёсткий потолок**, проверка `ORBIT_OVER_BUDGET`: сумма часов по
   `(инженер, орбита, спринт)` не больше `capacity_rate × 80`. Бронирования бюджета
   заранее нет: свои задачи получают приоритет порядком кандидатов.

**Ограничение.** Жадный алгоритм не переставляет уже принятые назначения, поэтому
случай, когда универсал уводит часы с роли, которую больше никто не закрывает, в
общем виде не решается. Его ограничивают порядок обхода, «своя орбита первым» и
атомарный режим. Полное решение — MILP (альтернатива в ADR-011).

**Как поменять.** Порядок кандидатов — `_candidate_engineers`, списание —
`_spend_from`, цель — `OBJECTIVE` в `app/planner/constants.py`.

## ADR-016. Часы исполнителя, `efficiency` и даты исходного плана

**Решение.**

1. **`plan_assignments.hours` — человеко-часы исполнителя.** Чтобы закрыть смету
   `remaining_hours` по роли, нужно `remaining_hours × efficiency` часов исполнителя
   (`_allocate_task`). Сейчас `efficiency = 1.00` везде, формула вырождается в
   тождество, но верна и после включения дообучения. Проверка `UNDER_ALLOCATED`
   остаётся нижней границей.
2. **Даты исходного плана — история, не обязательство.** `planned_start` и
   `planned_end` планирование не используют. Дедлайн считается от конца PI (красный
   `deadline_miss`), а выход прогноза за даты плана виден как warning
   `PLANNED_END_OVERSAIL`: показать, не блокировать.
3. **Окно задачи не выходит за квартал** — проверка `WINDOW_OUTSIDE_PI`.

Как SP списываются со спринтов — ADR-029.

**Как поменять.** `EFFICIENCY_NOTE` и формула в `_allocate_task`; даты — проверка
`PLANNED_END_OVERSAIL`.

## ADR-017. Фонд пропорционален длине спринта

**Решение.** Фонд часов спринта пропорционален его длине. Единственный источник
множителя — две витрины, дублировать арифметику нельзя:

| Вьюха | Что даёт |
|---|---|
| `v_sprint_fund_factor` | `factor = length_days / sprint_length_days` по спринту |
| `v_pi_fund_factor` | `factor = Σ length_days / sprint_length_days` за PI |

Фонд спринта = `rate × fte_hours_per_sprint × v_sprint_fund_factor.factor`; фонд
квартала = `rate × fte_hours_per_sprint × v_pi_fund_factor.factor`. В текущем
календаре все спринты полные: множители равны 1,0000 и 6,0000, фонд полной ставки
за PI — 480 ЧЧ. Механика сохранена на случай спринта другой длины.

**Где применяется:** витрины `v_team_capacity_sp.available_sp_per_pi`,
`v_satellite_capacity.hours_own`, `v_role_supply_hh.hh_per_pi`,
`v_role_deficit_effective`, `v_role_coverage_org`; инварианты `SP_OVERFLOW`,
`ENGINEER_OVERLOAD`, `ORBIT_OVER_BUDGET`; планировщик (`_Funds`, проверка SP в
`place()`, фонд роли в оранжевых алертах); данные — `sprints.length_days`.

**Что видно в контракте.** `plan_runs.params.calendar` =
`{pi_start, pi_end, sprint_count, pi_days, fund_factor, fund_hh_per_fte,
short_sprints}`: прогон без границ PI невозможно сопоставить с кварталом.

**Как поменять.** Длины и границы — `etl/config.py`; множители считает БД
(`db/04_views.sql`).

## ADR-018. Контракт метрик: свои имена, свой формат, заморозка

**Решение.** Текст формата Prometheus 0.0.4 собирается вручную (`app/metrics.py`),
`prometheus_client` не используется: процесс один, эндпоинт один, а лишняя
зависимость дороже десятка строк форматирования. Имена метрик — контракт: префикс
`pi_planner_` обязателен, переименование — breaking change и объявляется отдельно.

`pi_planner_plan_kpi_value` и оба порога имеют метки `kpi`, `sprint`, `kind`
(`forecast` или `actual`). KPI, решения и алерты относятся к последнему успешному
прогону, как в интерфейсе; `pi_planner_plan_last_run_*` описывают последнюю
попытку расчёта, а `pi_planner_plan_active_run_id` — активный прогон.

Роли эндпоинтов жёстко разные: путаница liveness и readiness ломает мониторинг.

| Путь | База | Зачем |
|---|---|---|
| `/api/livez` | не трогаем | liveness: рестарт уместен, только если процесс мёртв |
| `/api/health` | да | readiness: 503, если база недоступна |
| `/api/version` | не трогаем | версии приложения, ETL и PI |
| `/api/views`, `/api/views/{view}` | да | витрины для фронта (ADR-019) |
| `/metrics` | да, с кэшем | scrape Prometheus |

**Почему `/metrics` отдаёт 200 даже при мёртвой базе.** Иначе мониторинг теряет
вместе с метриками и причину: `pi_planner_db_up 0` и
`pi_planner_db_metrics_error{error_class}` отвечают на вопрос «почему бизнес-серий
нет».

**Почему метка `route`, а не URL.** Имена файлов фронта меняются при каждой сборке:
с URL в метке кардинальность росла бы. Набор маршрутов фиксирован: известные
эндпоинты, один шаблон `/api/views/{view}` на все витрины, `/api/*` и `/static`.
Расширение набора — объявляемое изменение.

**Почему бизнес-метрики под кэшем.** `v_plan_violations` — объединение десятков
проверок; считать её на каждый scrape незачем. Снимок обновляется раз в
`PI_PLANNER_METRICS_TTL` (15 с по умолчанию), в том числе при ошибке: упавшая база
не должна получать запросы чаще здоровой.

**Чем платим.** Метрик меньше, чем дал бы `prometheus_client`: нет бакетов
гистограмм и квантилей, нет `process_*` и `python_*`.

**Как поменять.** Имена и метки — `app/metrics.py`; маршруты и логи —
`app/server.py`; конфиг Prometheus, алерты и Caddy — [OBSERVABILITY.md](OBSERVABILITY.md).

## ADR-019. Витрины для фронта: одна строка как есть, маршрут — параметр

**Решение.** `GET /api/views/{view}` отдаёт «строку витрины как есть» плюс конверт
(`view`, `run_id`, `as_of`, `count`, `columns`, `items`); имя витрины — параметр
пути, а не отдельный маршрут.

**Почему не эндпоинт на экран:** бэкенд переписывал бы одну витрину по разу на
экран, а каждый новый экран расширял бы замороженный набор меток `route`
(ADR-018). **Почему не произвольный `SELECT`:** параметр стал бы SQL-инъекцией, а
внутренняя кухня ETL уехала бы наружу.

Имена витрин — имена объектов в БД: они описаны в [SCHEMA.md](SCHEMA.md), и второй
словарь «публичных» имён порождал бы расхождения. Защита:

* имя витрины не подставляется в SQL, только словарь `app/views.SOURCES`, иначе 404;
* `ORDER BY` собирается из `orderable` конкретной витрины, иначе 400;
* `run_id`, `limit`, `offset` — параметры (`%s::int`); `limit` ≤ 5000;
* всё идёт в read-only сессию.

Внутрь не пускаем кухню ETL (`load_batches`, `role_aliases`, `task_sequence`,
оценки, `pi_periods`) и промежуточные вьюхи (`v_role_supply_hh`,
`v_backlog_demand`): у экранов есть готовые витрины с вердиктом.

**Фильтров на сервере нет:** данных мало, клиентская фильтрация честнее, чем
параметризация SQL под каждый экран. Понадобится — добавится `where` по тому же
белому списку колонок. **`run_id` по умолчанию** — последний удачный прогон
(`MAX(run_id) WHERE status IN ('ok', 'infeasible')`): фронт, бэкенд и приёмка не
расходятся в том, какой прогон «текущий». `count` — отдельный запрос только при
обрезании. `NULLS LAST` в обе стороны: у переносов `start_sprint` пуст, и без этого
«не запланировано» оказалось бы первым.

**Чем платим.** Фронт видит сырые колонки и может повторить запрещённые
вычисления: сложить часы ролей в часы задачи (ADR-002), посчитать фонд константой
(ADR-017), вывести знаменатель KPI из `committed_week0` (ADR-004). Технически это не
поймать: запрет живёт в [UI_SPEC.md](UI_SPEC.md) и в текстах на экранах. Поэтому
UI_SPEC — часть контракта.

**Как поменять.** Белый список и SQL — `app/views.py`; маршруты и коды —
`app/server.py`; метка маршрута — `app/metrics.py`; тесты — `tests/test_views.py` и
`tests/test_server.py`.

## ADR-020. Story Points как поток по спринтам

Заменено ADR-029: SP и часы размещаются вместе. Из этого решения остаётся
правило пересчёта: входной `estimation_sp` — исходный размер задачи; колонка
`completed_sp` в отчёте — подтверждённый объём **за этот спринт**, а не
накопительный итог; остаток нового плана равен
`estimation_sp − SUM(completed_sp)` по принятым отчётам; пустая ячейка означает, что
объём не подтверждён, потраченные часы в SP автоматически не превращаются; сумма
подтверждённых SP не превышает исходный размер задачи. Инвариант `SP_OVERFLOW`
суммирует доли по команде и спринту, `SP_SHARES_MISMATCH` проверяет, что сумма
долей равна остатку SP в снимке прогона.

## ADR-021. Факт спринтов: журнал загрузок и воспроизведение состояния

**Контекст.** Раз в две недели загружаются фактические результаты спринта, и сервис
пересчитывает оставшуюся часть плана.

**Решение.** Три уровня:

* **журнал** — `actual_uploads`, `task_actuals`, `task_actual_spent`: одна загрузка —
  факт одного спринта;
* **воспроизведение** — функция `apply_actuals()` пересобирает текущее состояние
  задач из снимка датасета (`tasks_seed_state`, `task_role_spent_seed`) плюс закрытые
  загрузки по порядку. Идемпотентна;
* **приём** — `POST /api/actuals?sprint=N` проверяет файл целиком и, если есть хоть
  одна ошибка, не принимает ничего.

Загрузка факта спринта N заменяет прежний факт N и все более поздние вместе с
построенными на них прогонами: иначе факт спринта 3 висел бы на заменённом факте
спринта 2. Прежние версии файлов сохраняются (ADR-034).

Дата загрузки и дата события — разные вещи: `actual_uploads.loaded_at` фиксирует
получение отчёта, `task_actuals.actual_end` — завершение задачи. Начало не может
быть позже конца, даты не бывают будущими, завершение `Done` должно быть внутри PI и
не позже конца отчётного спринта. Пустой конец первого `Done` означает конец
отчётного спринта. Завершение из более раннего спринта можно сообщить поздно: оно
относится к спринту своей даты. Для дат пустая ячейка значит «не передано»,
`CLEAR` или `очистить` — явное очищение, новая дата — исправление. При
воспроизведении статус берётся из последней строки задачи, а начало и конец —
независимо из последнего явного события каждого поля. Повторный `Done` с пустым
концом сохраняет прежнее завершение; очистить конец у `Done` нельзя.

`actual_uploads.plan_run_id` хранит прогон, с которым сравнивался факт при приёме.
`v_sprint_deviation` берёт состояние задачи только из загрузок не позднее
отчётного спринта и исходного снимка, а не из сегодняшнего `tasks`. В отчёт входят
и выполненные вне плана задачи; поздний `Done` выделяется отдельно.

Загрузка датасета или факта, пересчёт и независимая проверка плана выполняются в
одной транзакции PostgreSQL с согласованным снимком чтения; промежуточное состояние
читателям не видно, ошибка откатывает и новые данные, и удаление прежних прогонов.
HTTP-загрузка и `tools/run_planner.py` берут одну advisory-блокировку PostgreSQL до
открытия снимка `REPEATABLE READ`: второй писатель ждёт публикации первого и читает
уже новую версию.

**Почему `tasks` изменяемый.** Альтернатива — «эффективный статус» поверх
неизменяемого ядра — потребовала бы переписать десяток витрин и инвариантов. Вместо
этого журнал хранит факты, а `tasks` — ТЕКУЩЕЕ состояние, всегда выводимое из
журнала. Прогоны сверяются со своим слепком `task_state`, а не с сегодняшним
`tasks`, поэтому старый прогон не становится «ошибочным», когда задача позже
закрылась.

**Проверка.** `tools/demo_cycle.py` отыгрывает три спринта с отклонениями и
пересчётами; файлы лежат в `demo/` и загружаются через интерфейс.

## ADR-022. Причина у каждого решения и сценарий следующего PI

**Решение.** У каждой строки расписания есть `reason_code` (справочник
`ref_decision_reasons`), `reason_text` — готовое предложение по-русски — и
`reason_details` с разбивкой. Причина определяется по фактическому состоянию фонда
после всех проходов, а не по тому, на каком шаге задача выпала:

| Код | Когда |
|---|---|
| `PLANNED` | включена: приоритет, место в очереди, кто закрывает роли, займы, растяжка SP |
| `ROLE_NOT_IN_STAFF` | нужной роли нет в штате: перечислены роли и часы |
| `SKILL_UNAVAILABLE` | роль есть, но нет инженера с подтверждённым стеком |
| `ROLE_HOURS_EXHAUSTED` | часов роли не осталось: сколько нужно, сколько свободно, кто занял |
| `TEAM_SP_EXHAUSTED` | ёмкость команды выбрана: сколько SP нужно и сколько свободно |
| `GRAPH_HORIZON` | цепочка зависимостей выводит самый ранний старт за конец квартала (ADR-031) |
| `BLOCKED_BY_DEFERRED` | ждёт перенесённую блокирующую задачу |
| `INITIATIVE_ATOMIC` | перенесена вместе с инициативой (режим `atomic`) |
| `ETC_REQUIRED` | остаток работ неизвестен (ADR-026) |
| `PI_CLOSED` | квартал закончился |
| `NOT_FEASIBLE_NEXT_PI` | зарезервирован: автоматическая отмена не выдаётся |

Для совместимости в колонке `decision_reason` дублируются коды `M2` (нет ресурсов) и
`M3` (нет готовности смежных команд).

**Сценарий следующего PI.** Задачи, перенесённые из-за нехватки ресурсов,
раскладываются с тем же штатом и календарём, без нового бэклога и найма. Не
вошедшая задача проверяется отдельно: если она помещается, причина — конкуренция за
фонд; если нет, нужны пересмотр объёма, декомпозиция или ресурс. Оба случая
остаются переносом, отмена требует отдельного бизнес-решения. Роли, которых нет в
штате, в симуляцию не идут: такие работы переносятся до найма или дообучения.

**Проверка.** Инвариант `DECISION_WITHOUT_EXPLANATION`: решение без кода и текста —
ошибка приёмки.

## ADR-023. KPI по формулам постановки: прогноз отдельно от факта

**Решение.** У `kpi_snapshots` есть колонка `kind`:

* `forecast` — по текущему плану; есть всегда;
* `actual` — по загруженному факту; появляется после первой загрузки.

Знаменатель «процента выполнения квартала» — инициативы, у которых **все** живые
задачи Недели 0 стояли в квартале: только их план обещал завершить. Частично
включённые считаются отдельно (`partial_initiatives`) и в знаменатель не входят,
иначе показатель наказывал бы за честно показанный частичный охват.

«Выполнение плана спринта»: знаменатель — SP задач, которые первоначальный план
закрывает в этом спринте; числитель — SP задач с подтверждённой датой завершения в
этом спринте, даже если отчёт поступил позже (для будущих спринтов — прогноз
текущего плана). Фактическая предсказуемость учитывает только завершения внутри PI.

**Норма Bus Factor — не ниже 2:** требование «Bus Factor больше 1», при пороге 1
значение 1 попадало бы в норму.

## ADR-024. Bus Factor по компетенциям, а не по ролям

**Решение.** `v_bus_factor_skill`: для каждого заявленного навыка — число
носителей, команды, роли и градация риска:

* **нет носителей требуемого навыка** — спрос подтверждён, носителей нет;
* **критично** — единственный носитель навыка, на который есть подтверждённый спрос;
* **предварительно: один носитель роли** — единственный носитель, спрос оценён
  только через роль;
* **единственный носитель** — навык у одного, спроса пока нет;
* далее «два носителя» и «ок».

Покрытие ролей (роли, которых нет в штате) остаётся отдельной величиной —
`v_bus_factor` и `v_role_coverage_org`: это вопрос найма, а не незаменимости.
Смешивать их нельзя, они лечатся по-разному.

«Где отсутствие одного сотрудника создаёт риск» — `v_engineer_absence_risk`: для
каждого инженера задачи текущего плана, у которых нет запасного исполнителя по
фонду и подтверждённому стеку. Полный сценарий с перестроением плана —
`GET /api/scenarios/absence`.

**Ограничение.** Спрос на навык берётся из подтверждённой разметки «задача × роль ×
навык» (`app/skill_review.py`); для неразмеченных задач он оценивается через роль
носителя и помечается как приближение (`demand_source = role_proxy`).

## ADR-025. Квартал — шесть двухнедельных спринтов

**Решение.** Начало PI — начало календарного квартала (ответ заказчика №5), длина —
ровно 6 × 14 = 84 дня, как требует постановка: «шесть двухнедельных спринтов —
12 недель», KPI считается по инициативам, «завершённым в течение 12 недель»,
лимит — «до 80 часов за спринт». Для Q3-2026 это **01.07–22.09.2026**, фонд полной
ставки — 480 ЧЧ. Остаток календарного квартала в сетку планирования не входит.

**Почему не семь спринтов.** Семь спринтов противоречат постановке в трёх местах:
«шесть спринтов», «12 недель» в формуле KPI и «до 80 часов за спринт».

**Как поменять.** `etl/config.py`: `PI_START`, `SPRINT_COUNT`, `SPRINT_LENGTH_DAYS`;
`PI_END` вычисляется из них. Механика множителей фонда (ADR-017) сохранена на
случай спринта другой длины.

## ADR-026. Оценка оставшейся работы не выводится из потраченных часов

**Решение.** `task_role_estimates` хранит исходную смету, `task_role_spent` —
накопленный факт, `task_role_etc` — версионированную оценку остатка по роли с
обязательной причиной. Последняя ревизия ETC определяет потребность планировщика.
Новая ревизия добавляется строкой, прежняя остаётся для аудита.

| Состояние роли | Остаток | Признак |
|---|---|---|
| есть ETC | значение ETC | — |
| ETC нет, факта нет | смета | — |
| ETC нет, факт меньше сметы | смета − факт | `remaining_provisional` (не подтверждён) |
| ETC нет, факт не меньше сметы, задача не `Done` | 0 | `remaining_unknown` |

Задача переносится с `ETC_REQUIRED` только если **ни по одной роли не осталось
работы**: исчерпанная роль при живых остальных задачу не блокирует. Нулевой
расчётный остаток и фиктивное назначение 0,01 ЧЧ не означают готовность.
Предварительный остаток помечается в причине решения. Чтобы уточнить задачу,
добавляют строку, например
`INSERT INTO task_role_etc (task_id, role_id, remaining_hours, reason) VALUES
('A', 1, 40, 'оценка после ревью');`, и запускают пересчёт плана.

## ADR-027. Доступ: токены, три роли, журнал действий

**Контекст.** Сервис пишет в базу, `POST /api/dataset` стирает цикл квартала, а
раздача статики не должна позволять прочитать произвольный файл контейнера.

**Решение.**

1. **Токен в заголовке** `Authorization: Bearer …`, не cookie: CSRF через чужую
   страницу невозможен. В базе только SHA-256 токена (`app_users`).
2. **Роли** `viewer` < `planner` < `admin`. Читать витрины — viewer; загружать факт,
   подтверждать ETC и результаты — planner; загружать датасет — admin. Неизвестный
   маршрут записи требует admin.
3. **Режимы** `PI_PLANNER_AUTH=required` (по умолчанию) и `off` (только для доверенной
   машины, в логе предупреждение). Аварийный администратор —
   `PI_PLANNER_ADMIN_TOKEN` (не короче 16 символов), работает и при недоступной базе.
   Пользователей создаёт `tools/manage_users.py`.
4. **Публично** остаются `/api/livez`, `/api/health`, `/api/version` (без токена —
   урезанные ответы без адреса базы и версий) и статика фронта. `/metrics` закрывает
   Caddy.
5. **Перебор токенов:** 10 неудач за минуту с одного адреса → 429.
6. **Аудит:** `audit_log` (кто, что, итог) и поля `uploaded_by`, `loaded_by`,
   `revised_by`; `confirmed_by` результата берётся из токена, а не из тела запроса.
7. **Статика:** путь раскрывается `resolve()` до проверки границы; заголовки
   `X-Content-Type-Options`, `X-Frame-Options`, CSP отдаёт само приложение.

В набор маршрутов (ADR-018) входит `/api/me`.

**Что не делается.** Нет SSO и срока жизни токена: токен отзывается
`manage_users.py disable`. Для публичного доступа сервис ставят за HTTPS (Caddy).

## ADR-028. Зависимости по умолчанию: `finish_start`

**Решение.** Значение по умолчанию — `finish_start`:
`start(blocked) ≥ end(blocking) + gap`. Блокируемая задача не может закончиться
раньше предшественника. `start_start` остаётся явным режимом
(`--dependency-mode start_start`). Константа `DEFAULT_DEPENDENCY_MODE` одна на
`build_plan`, алерты, сценарий отсутствия и CLI. Независимая проверка (`F` и
`START_BEFORE_EARLIEST`) читает режим из `plan_runs.params`, поэтому прогоны,
построенные в другом режиме, проверяются по своим правилам.

**Следствия.** На данных с длинными цепочками плановые сроки зависимых сдвигаются
вправо: это цена корректности. Предпосчитанный ETL-граф остаётся нижней границей
(для `finish_start` она слабее), точную границу на дату прогона задаёт
`plan_dependency_bounds`.

## ADR-029. SP и часы размещаются вместе

**Решение.** Одно размещение. Для спринта `s` работа задачи ограничена
`ΣH × free_s / SP`, где `free_s` — свободная ёмкость команды в SP, `ΣH` — работа по
всем ролям. Роли закрываются независимо внутри этого бюджета. После размещения доля
SP спринта пропорциональна его работе, округляется вниз до сотой, недостающие сотые
раздаются по наибольшим остаткам только там, где есть место; не удалось —
кандидат старта отвергается. Кусок работы меньше `MIN_CHUNK_HH` = 1 ч не
планируется, если им не закрывается роль.

**Что не меняется.** SP и часы остаются разными величинами; универсального
перевода нет. Остаток SP задачи в работе определяет подтверждённый `completed_sp`
(ADR-020).

**Следствия.** Спринт с долей SP всегда содержит часы, спринт с часами — долю SP;
дата результата — последний спринт с работой. Метки `team_sp_only` и
`engineer_hours_only` в `v_plan_task_progress` не возникают (колонка сохранена).
Кандидаты старта, при которых доли SP не помещаются в ёмкость из-за округления,
отвергаются: задача стартует позже, а не нарушает `SP_OVERFLOW`.

## ADR-030. Ёмкость команды: история плюс закрытые спринты текущего PI

**Решение.** Нормативная ёмкость и базовый план — `среднее(team_history) ×
focus_factor`. Пересчёт на начало спринта `k` берёт среднее по `team_history` **и**
по наблюдениям закрытых спринтов `1..k−1` (поровну), затем умножает на
`focus_factor`. Наблюдение — SP, поставленные командой за спринт (подтверждённый
прогресс плюс остаток SP завершённых задач); спринт без поставки — нулевое
наблюдение для команд с бэклогом. Ёмкость прогона фиксируется в
`plan_team_capacity` и `params.capacity_model`; независимая приёмка сверяет план с
этим снимком.

**Почему так.** Иначе команда, провалившая спринт, в пересчёте планировалась бы с
прежней скоростью: пересчёт оптимистичен именно там, где должен предупреждать.

**Почему равные веса.** Выборка мала, любая схема весов выглядела бы точнее, чем
есть. Равные веса прозрачны и воспроизводимы; версия модели записана
(`capacity_model.version = 1`), смену весов делают новой версией.

**Ограничения.** Если команда не сообщает `completed_sp`, её поставка учитывается
только завершёнными задачами, и скорость занижается (консервативно). Остаток SP
завершённой задачи включает долю, сделанную до квартала. Команда без истории
блокирует загрузку (`TEAM_WITHOUT_HISTORY`).

## ADR-031. Объяснение отказа строится из той же проверки, что и решение

**Решение.**

1. `_allocate_task` ведёт журнал попытки (`log`): по спринту — свободные SP, бюджет
   работы по SP, размещённая работа, признак «работу ограничила ёмкость SP»; в конце
   — недоразмещённый остаток по ролям. Объяснение берёт числа из журнала той же
   проверки совместной выполнимости (ADR-029), что и размещение.
2. Различаются причины: `ROLE_HOURS_EXHAUSTED` (не удалось разместить X из Y ЧЧ,
   свободно Z, а если Z хватает — «часы не собираются в нужные спринты»),
   `TEAM_SP_EXHAUSTED` (часов хватает, SP по спринтам и кто их занял), `GRAPH_HORIZON`
   (самый ранний старт за пределами квартала и какие блокирующие его задают),
   `INITIATIVE_ATOMIC` (задача помещается по часам **и** SP).
3. Конкуренты называются поимённо с местом в очереди; «выше в очереди» пишется
   только тем, кто действительно выше (`higher_priority`), остальным — «ниже в
   очереди (занято из-за порядка размещения)».

**Проверка.** Юнит-тесты фиксируют числа в объяснении, по ним отказ подтверждается
вручную.

## ADR-032. Приоритет инициативы: явный бизнес-приоритет и сравнимые стратегии

**Контекст.** `MAX(rung)` (ADR-005) в неоднородной инициативе поднимает весь пакет
из-за одной срочной задачи, а режим `greedy` допускает частичные инициативы.
Бизнес-цель неизвестна, поэтому ни одну эвристику нельзя объявить правильной.

**Решение.**

1. **Явный бизнес-приоритет** `initiatives.business_priority` (плюс кто, когда,
   основание). Его задаёт человек (роль `planner`, `POST /api/initiatives/priority`,
   кнопка в заголовке инициативы на Ганте); он главнее датасета и любой стратегии.
   Основание обязательно; сохранение пересчитывает план, действие пишется в журнал.
2. **Стратегия** — параметр прогона `priority_strategy` (в `plan_runs.params`):
   `max` (по умолчанию), `task` (по собственному rung задачи), `weighted`
   (средневзвешенный по SP rung живых задач), `completion_first` (при равном
   приоритете раньше инициатива, которую дешевле завершить). Пересчёты наследуют
   режимы базового прогона.
3. **Сравнение.** `tools/compare_priority.py` строит план для каждой стратегии на
   одних ресурсах и показывает, как меняется состав квартала.

Если узкое место — отсутствующие роли, все стратегии дают один состав квартала; это
измеряется командой `compare_priority.py`, а не предполагается. Различия появляются,
когда ресурс действительно оспаривается.

**Что не делается.** Нет ценностного скоринга: данных о ценности в датасете нет, её
вводит бизнес через явный приоритет.

## ADR-033. Доступность инженера по спринтам

**Решение.** `engineer_orbit_availability` хранит исключение по инженеру, орбите, PI
и спринту с источником. Без записи используется штатная
`engineer_orbits.capacity_rate`. Сумма ставок орбит не может превышать ставку
инженера. Планировщик и `v_satellite_capacity` используют один календарь; снимок
фонда прогона фиксирует результат. Изменение через API пересчитывает план
атомарно. Дополнительная квалификация с датами и источником хранится отдельно и
сама по себе не разрешает назначать инженера на другую роль.

**Ограничение.** Календарь задаётся для существующего инженера и орбиты; кадровые
события и графики часов внутри спринта не моделируются.

## ADR-034. Редакции исходных загрузок

**Решение.** `upload_revisions` сохраняет байты новой загрузки, связь замещения и
ответ на запрос с `Idempotency-Key`. Перед заменой фиксируется снимок активного
отчёта, прогонов, KPI и расписания. Браузер повторяет тот же ключ после сетевого
сбоя и выдаёт новый ключ для следующей осознанной загрузки.

**Ограничение.** После исправления спринта N отчёты N+1 и далее доступны для
скачивания, но заново загружаются оператором по порядку. Для загрузок, созданных до
появления архива, исходных байтов нет.

## ADR-035. Сравнение вариантов плана

**Решение.** В режиме `atomic` после первой упаковки выполняется повторная упаковка
инициатив. Экран качества сравнивает `greedy` и `atomic` на одном входе. Для входа до
пяти инициатив и десяти задач перебираются все порядки инициатив; результат точен
среди этих порядков при том же алгоритме размещения. Сумма SP живых задач служит
верхней границей, SP завершённых инициатив — технической мерой. Эти величины не
называются бизнес-ценностью.

**Ограничение.** Перебор порядков не доказывает глобальный оптимум по всем
допустимым расписаниям: для этого нужна отдельная точная модель ограничений.
