«делает ли пункт продукт правильнее и надёжнее», а не «успеем ли до сдачи».
Ниже по каждому пункту:

- **Вердикт:** принять / принять с поправкой (суть верна, решение предлагаем
  другое или уточнённое) / отклонить.
- **Проверка:** «подтверждено» — я сам проверил по коду или прогоном;
  «по коду аудита» — утверждение правдоподобно и согласуется с прочитанным

- **Объём:** S — до полудня, M — 1–2 дня, L — больше, затрагивает контракт/схему.

## S. Дополнения, отсутствующие в аудите (делать первыми)

### S-1 — Path traversal в раздаче статики · P0 · подтверждено · S
`app/server.py:485`: `target = DIST / rel` не нормализуется, `is_relative_to` —
лексическая проверка. `/%2e%2e/%2e%2e/...` отдаёт любой файл контейнера, включая
`/proc/self/environ` с DSN и паролем БД.
**Как:** `target = (DIST / rel).resolve()` и проверка `is_relative_to(DIST.resolve())`;
тест на `..`, `%2e%2e`, `..%2f`, симлинк.

### S-2 — Запись без аутентификации · P0 · подтверждено · M
`POST /api/dataset` стирает весь цикл, `POST /api/actuals` переписывает факт —
доступны любому, кто видит сервис. Для продукта нужна модель доступа.
**Как:** минимум — сессия/токен и роли `viewer` / `planner` / `admin`
(загрузка датасета — только `admin`); журнал «кто загрузил» в `actual_uploads`
и `load_batches`; CSRF-защита для POST из браузера. Caddy может дать
forward-auth, но проверка прав должна быть в приложении.

### S-3 — Выбранный прогон «залипает» · P1 · подтверждено · S
`web/src/hooks/useRun.tsx:39`: `selected` не сбрасывается после загрузки, а
`run_id` после нового датасета начинается с 1 (`RESTART IDENTITY`). Покрывается
DA-49 частично; выделено, потому что ломает экран сразу.
**Как:** `selected` валиден, только если он есть в `runs`; после загрузки —
переход на созданный `run_id` из ответа.

## 3. Компетенции и звёздная карта

### DA-01 — Нет проверки требуемых технологий · принять · подтверждено · L
PDF, раздел «В»: «система не может назначить инженера, если в его профиле нет
требуемых технологий» — **это явное правило задачи**, а у нас кандидаты
подбираются только по роли (`planner.py:674`, `_candidate_engineers`).
Связи «задача → навык» в Excel нет, значит в продукте нужна сущность
требований и способ её заполнить.
**Как:**
1. Таблица `task_skill_requirements(task_id, role_id, skill_id, source, status)`,
   `source ∈ {manual, rule, inferred}`, `status ∈ {proposed, confirmed}`.
2. Начальное заполнение — правило «роль сметы → базовый стек роли» (`source=rule`,
   словарь в конфиге, как `ROLE_ALIASES`) + опциональный разбор `summary` по
   словарю навыков (`source=inferred`, только `proposed`).
3. Планировщик: в кандидаты попадает инженер, у которого есть все
   `confirmed`-навыки задачи по роли; `proposed` — не ограничение, а пометка
   в причине решения («стек не подтверждён»).
4. UI: редактирование требований на карточке задачи; DQ-правило «у задачи нет
   подтверждённых требований».
5. Новый код причины `SKILL_NOT_AVAILABLE` в `ref_decision_reasons`,
   инвариант `ASSIGNEE_LACKS_SKILL`.
**Важно:** не выдавать выведенные требования за данные заказчика — в отчётах
и README явно разделять «из датасета» и «правило/вывод».
**Зависит от:** DA-02 (канонические навыки).

### DA-02 — Синонимы и составные навыки · принять · подтверждено · M
В `build/seed.sql`: `Kafka`/`Apache Kafka`, `Core Spring`/`Spring Core`/`Core`,
`Microservices`/`Microservices Архитектура`/`Микросервисы`, `CI/CD`/
`CI/CD (GitLab, Jenkins)`/`GitLab CI`, `Регресс`/`Regression/Smoke/Functional testing`,
`REST API`/`REST/gRPC`/`REST/SOAP интеграции`.
**Как:** `skills` → канонические навыки + `skill_aliases(raw_text, skill_id,
status)`; правила разбора составных («A/B» → два навыка, «X (A, B)» → X + A + B,
по словарю, не автоматически); исходный текст хранится в `engineer_skills.raw`.
Неоднозначные — в очередь разбора (DQ). Java ≠ JavaScript — явный тест.

### DA-03 — Критичность навыка через уникальность роли · принять · подтверждено · M
`v_bus_factor_skill`: `sole_in_role` не требует `in_demand`, а KPI фильтрует
`in_demand` — разные совокупности. И верно, что второй Java-разработчик без Kafka
не страхует носителя Kafka.
**Как:** критичность = навык требуется живой работе (из DA-01) ∧ носителей
с этим навыком и свободной ёмкостью < 2. До готовности DA-01 — явная пометка
«оценка через роль (приближение)» в UI и `details`. KPI и список критичных —
из одной витрины.
**Зависит от:** DA-01, DA-02.

### DA-04 — «Есть замена» без проверки ёмкости · принять · по коду аудита · M
`v_engineer_absence_risk`: `tasks_without_backup` пуст, если по роли ≥ 2 человек,
независимо от их загрузки.
**Как:** (1) в витрине — кандидат-замена считается, только если у него есть
нужный стек и свободные часы в спринтах задачи; (2) сценарий «инженер X
недоступен с спринта k» — тот же механизм, что NEW-02 (сценарный прогон),
с diff по инициативам и срокам. Число коллег по роли — отдельная справочная
колонка.
**Зависит от:** DA-01, NEW-02, DA-14.

## 4. Остатки работ, ресурсная модель и решения планировщика

### DA-05 — Потраченные часы = выполненная работа · принять · подтверждено · M
`v_task_remaining_hh` = `max(смета − факт, 0)`; при нуле — символическое
назначение 0.01 ЧЧ и текст «работа фактически выполнена» (`planner.py:772`,
`:1309`). На исходных данных MOB-7011 (165/165 ЧЧ, InProgress).
**Как:**
- в факт добавить колонки «остаток, ЧЧ» по ролям (ETC); хранить
  `original_estimate`, `spent`, `etc`, `etc_reason`, `etc_source`;
- `remaining = ETC`, если задан; иначе `max(смета − факт, 0)`, **но** если
  результат 0 у незакрытой задачи — статус `needs_reestimate`, задача не
  планируется как готовая, жёлтый алерт `overrun`, причина в UI;
- убрать `SYMBOLIC_HOURS`: разрешить `in_quarter` без назначений для задач с
  нулевым остатком, ожидающих только закрытия, и поправить инвариант
  `IN_QUARTER_WITHOUT_ASSIGNMENTS` (исключение по явному статусу).

### DA-06 — SP повторно списываются целиком · принять с поправкой · подтверждено · M
`_sp_flow` всегда начинает с `estimation_sp`; `remaining_sp` в `task_state` =
исходный SP.
**Поправка к решению:** аудит предлагает «явно учитывать подтверждённый
выполненный объём». Конкретно: выполненный SP = сумма плановых долей
`plan_task_sp` действовавшего плана за закрытые спринты, если задача по факту
в работе и не отстаёт (по ETC); при отставании — пропорция ETC к исходной
оценке часов, с пометкой источника. Это согласовано с потоковой моделью
ADR-020 и не превращает часы в SP напрямую.
Инвариант `SP_SHARES_MISMATCH` — сумма долей = `remaining_sp`, а не
`estimation_sp`.
**Зависит от:** DA-05 (ETC), DA-07.

### DA-07 — SP и часы раскладываются независимо · принять с поправкой · по коду аудита · L
Действительно: окно = max(часы, SP), бывают спринты «SP без людей».
**Поправка:** предлагаю конкретную семантику вместо открытого выбора:
SP — пропускная способность команды, часы — работа людей; **доля SP в спринте
пропорциональна доле часов задачи в этом спринте**, ограничение — свободная
ёмкость команды. Если ёмкости не хватает — часы этого спринта тоже
сдвигаются (одно совместное размещение, а не два последовательных).
Инвариант: спринт с SP > 0 обязан иметь часы > 0 и наоборот (кроме задач с
нулевым остатком, DA-05).
**Зависит от:** нет; делать вместе с DA-06 и DA-08 — один рефакторинг размещения.

### DA-08 — Парттаймер получает только одну орбиту на назначение · принять · подтверждено · L
PK `plan_assignments (run_id, task_id, sprint_no, engineer_id, role_id)` без
`home_team_id` → `_spend_from` берёт часы ровно с одной орбиты.
**Как:** включить `home_team_id` в PK (или отдельная таблица источников часов
назначения); `_spend_from` списывает с нескольких орбит; инварианты
`ENGINEER_OVERLOAD`/`ORBIT_OVER_BUDGET` уже считают суммы — проверить, что
не дублируют. Миграция в `db/migrations/`.

### DA-09 — Семантика зависимостей и инвариант F · принять · подтверждено · S
F (`db/05_invariants.sql:102`) сравнивает только старты и не читает
`plan_runs.params.dependency_mode`.
**Как:** решение по семантике — все три типа рёбер в датасете означают
предшествование, поэтому дефолт `finish_start`: `start(B) ≥ end(A) + gap`.
`start_start` оставить как явный режим. F читает режим из `params` и
проверяет соответствующее условие; негативный тест в `tools/negative_test.sql`.
Обновить ADR-013.

### DA-10 — Граф не пересчитывается по факту · принять · по коду аудита · M
`task_sequence` считается один раз в ETL.
**Как:** перенести расчёт графа в планировщик (или SQL-функцию) на дату
прогона: Done-узлы — с фактической датой завершения как ограничение;
различать старт задачи и старт остатка; `on_critical_path` переименовать в
`on_longest_chain` или считать настоящий критический путь с длительностями
из плана.
**Зависит от:** DA-26 (корректная обработка циклов).

### DA-11 — MAX(rung) поднимает всю инициативу · принять · по коду аудита · M
**Как:** отдельные поля `initiatives.business_priority` (вводит пользователь,
по умолчанию MAX(rung) с пометкой источника) и `tasks.rung`; стратегия
агрегации — параметр прогона (`max | weighted | completion_first`) в
`params`; экран сравнения стратегий на одном входе (через NEW-02/NEW-05).
Поправить обоснование ADR-005.

### DA-12 — Качество жадного плана не измеряется · принять · по коду аудита · L
**Как:** (1) метрики качества прогона в `params`: завершённые инициативы,
частичные, простой дефицитных ролей, доля использованной ёмкости;
(2) повторная упаковка для `atomic`; (3) опциональный движок на CP-SAT
(OR-Tools) за тем же интерфейсом `build_plan`, сравнение с greedy на наборе
контрпримеров с известным оптимумом. Greedy остаётся эталоном объяснимости.
**Зависит от:** DA-05–08 (сначала правильная модель, потом оптимизация).

### DA-13 — Отмена без доказательства невыполнимости · принять · по коду аудита · S
Симуляция следующего PI — один жадный прогон пула; проигравший в конкуренции
получает `NOT_FEASIBLE_NEXT_PI`.
**Как:** для каждой задачи пула — отдельная проба «одна в пустом PI»;
не влезает и одна → `NOT_FEASIBLE` (с указанием ограничения: роль/часы/SP/граф);
влезает одна, но не в общем прогоне → новый код `COMPETES_NEXT_PI`
(«перенос, конкурирует за ресурс с …»). Для задач, которые не влезают даже
одни, — рекомендация декомпозиции. Допущения симуляции — в `details`.

### DA-14 — Доступность постоянна на весь PI · принять · по коду аудита · L
**Как:** `engineer_availability(engineer_id, team_id, sprint_no, rate, reason)`
поверх `engineer_orbits` (по умолчанию = ставка орбиты); отпуск, выход,

### DA-15 — Справочник целей R1–R6 не связан с решениями · принять · по коду аудита · M
**Как:** таблица соответствия `decision → result_option`, поля
`result_recommended` (система) и `result_confirmed` (заказчик) в
`plan_task_schedule`/отдельной таблице подтверждений; в UI «рекомендовано
системой» визуально отлично от «согласовано». Определить, какие R считаются
завершением для KPI (R4+ или R6) — параметр, по умолчанию Done.

### DA-16 — Диагностика причин расходится с механикой · принять · по коду аудита · M

**Зависит от:** DA-07, DA-08.

## 5. Качество входных данных и факта

### DA-17 — Даты факта не валидируются · принять · подтверждено · S
README обещает проверку «дата вне спринта» — её нет.
**Как:** в `parse_actuals`/`load_actuals`: `start ≤ end`; `end` не позже конца
отчётного спринта и не в будущем относительно даты загрузки; `end` вне PI —
ошибка для KPI этого PI. Разделить дату события и дату отчёта: в KPI Say/Do
спринт определяется по `actual_end`, а не по номеру загрузки
(`DONE_IN_SPRINT_SQL`). Поздний отчёт о прошлом спринте — через DA-49
(коррекция).

### DA-18 — Теряется ранее сообщённый `actual_start` · принять · подтверждено · S
`apply_actuals`: сброс к seed + последняя строка + `COALESCE(last, seed)`.
**Как:** старт = первый непустой по истории загрузок; конец = дата первого
Done (повторный Done не двигает); явная очистка — отдельная пометка в файле
(`-` или `clear`), пусто = «не передано».

### DA-19 — Частичный отчёт закрывает спринт для всех · принять · по коду аудита · M
**Как:** разделить «загрузить данные» и «закрыть спринт»: загрузок за спринт
может быть несколько (по командам), закрытие — отдельное действие с
проверкой покрытия (какие команды/задачи отчитались). Пересчёт `as_of N+1`
— после закрытия; до него — предварительный прогон с пометкой. В факте
различать пусто / 0 / «без изменений».
**Зависит от:** DA-44 (версии загрузок).

### DA-20 — Числа и заголовки допускают искажения · принять · подтверждено (NaN) · S
`Decimal('NaN') < 0` → `InvalidOperation` вне обработчика → 503.
**Как:** `is_finite()`, диапазон (0…N, порог переработки — предупреждение, не
запрет), округление до 0.01 с явным правилом; дубли канонических заголовков
(включая алиасы одной роли) — ошибка; заполненная неизвестная колонка — ошибка,
пустая — предупреждение; декодирование без `errors="replace"` (ошибка
кодировки — 400 с указанием строки).

### DA-21 — Факт не сверяется с ролями, статусом, фондом · принять · по коду аудита · M
**Как:** проверки: часы по роли без сметы → предупреждение «незапланированная
работа», предложение пересмотра сметы; часы на Done прошлых спринтов —
ошибка; ToDo с часами → автоматически InProgress или ошибка (политика);
InProgress→ToDo — предупреждение с причиной. Отдельная витрина
незапланированной работы. Факт по сотруднику — опциональная колонка
`engineer_id` (если заказчик её ведёт), тогда проверка перегрузки людей.

### DA-22 — Ошибки ETL не блокируют план · принять · по коду аудита · M
**Как:** severity `error` блокирует применение seed в `load_dataset`
(сейчас `dq` только возвращается); `warning` — нет. Для выданного Excel —
регрессионный тест «загружается без error» (сейчас 0 error, 35 warning,
3 info). Пропущенные сущности — с листом/ячейкой в `dq_issues.detail`.
**Зависит от:** NEW-01/DA-44 (чтобы старая версия оставалась активной при отказе).

### DA-23 — Пропуск, ноль, ошибка и округление смешаны · принять · подтверждено (int) · M
`etl/load.py:299`, `:312`: `int(num(...))` — дробные SP/rung обрезаются,
пустое → 0.
**Как:** явная схема блоков (обязательные колонки, типы); `None` ≠ 0; дробный
SP — ошибка или явное округление с warning; отрицательная смета — error;
формула без кэша (`data_only=True` → None при наличии формулы) — проверка
через второй проход без `data_only`; контроль числа строк блока и «хвоста»
после пустой строки. Адрес ячейки в каждой находке. CHECK `estimation_sp >= 0`,
`velocity_achieved >= 0` в схеме.

### DA-24 — Резервный источник оценки расходится с матрицей · принять · по коду аудита · S
**Как:** убрать подстановку `declared` в `estimated_hh_effective` без ролей —
