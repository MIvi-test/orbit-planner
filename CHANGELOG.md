# Changelog

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Записи пишутся
для пользователя и администратора сервиса: что есть и что изменилось в поведении,
данных и запуске. Причины решений — в ADR ([docs/DECISIONS.md](docs/DECISIONS.md)),
как это устроено — в [docs/ALGORITHMS.md](docs/ALGORITHMS.md).

Каждое изменение, заметное пользователю или администратору, добавляется в раздел
«Не выпущено».

## [Не выпущено]

### Планирование
- План квартала строится по шести двухнедельным спринтам; задачи раскладываются по
  приоритету с учётом часов, ёмкости команды в SP, зависимостей и навыков. Для
  каждой задачи — включённой или перенесённой — есть причина готовым текстом.
- Зависимости по умолчанию `finish_start`: блокируемая задача стартует после конца
  блокирующей; `start_start` включается явно.
- Часы и SP размещаются вместе: задача, у которой SP больше ёмкости спринта,
  растягивается минимум на два спринта.
- Ёмкость команды в пересчёте учитывает закрытые спринты текущего квартала; её
  основание сохраняется в каждом прогоне и видно на экране «Профили».
- Явный бизнес-приоритет инициативы (кнопка на Ганте, `POST /api/initiatives/priority`)
  и стратегии приоритета `max`, `task`, `weighted`, `completion_first`;
  `tools/compare_priority.py` сравнивает стратегии.
- Остаток работ без ETC считается как «смета − факт» и помечается «не подтверждён»;
  `ETC_REQUIRED` — только если не осталось работы ни по одной роли.
- Доступность инженера по спринтам и датированные подтверждённые квалификации.
- Разметка технологий задачи с подтверждением и пересчётом плана.

### Факт и KPI
- Загрузка факта спринта закрывает спринт только при полном подтверждённом отчёте;
  файл проверяется целиком, при любой ошибке ничего не принимается.
- KPI показывают прогноз и факт отдельными строками; рядом с процентом выполнения
  квартала — охват обязательств; промежуточный факт сравнивается с плановым
  накоплением; «план завершений» и «бюджет работ» названы отдельно.
- Неопределённые значения KPI показываются как `N/A` с причиной, а не как 0 или 100.
- Архив исходных файлов загрузок и прежних снимков KPI и расписания; ключ
  повторного запроса при сетевом сбое.

### Риски и сценарии
- Алерты трёх типов: дефицит роли, срыв квартала, каскадный сдвиг.
- Bus Factor по компетенциям и риск отсутствия инженера; сценарий отсутствия строит
  план без инженера, ничего не публикуя.
- Сценарии чувствительности (доступность −20%, остаток часов +20%, скорость
  команд −20%) и кадровые меры (наём, обучение, перевод 0,5 ставки).
- Качество и потери плана; сравнение режимов `greedy` и `atomic` и перебор порядков
  инициатив на малых входах.

### Данные
- Несколько PI и сценариев: каждый набор данных живёт в отдельной схеме
  PostgreSQL и выбирается в шапке интерфейса.
- ETL запоминает ячейку Excel каждого значения; решение прослеживается до источника
  (`GET /api/tasks/trace`).
- Блокирующие находки качества данных не дают построить план; рабочий список
  находок с решениями и выгрузкой в CSV, XLSX, JSON.
- Загрузка датасета занимает меньше секунды.

### Интерфейс
- Боковое меню с иконками, сворачивается до одних иконок; новый экран «Сводка» с
  главными цифрами квартала; экран «Данные».
- Пять палитр (Стандартный, Розовый, Кровавый, Фиолетовый, Империум), у каждой
  светлый и тёмный режим; по умолчанию стандартная тёмная. «Империум» включается
  иконкой аквилы и меняет оформление, шапку, индикаторы, уведомления и подписи.
- Шрифты хранятся в приложении (больше не подгружаются с внешнего сервера).
- Звёздная карта: приближение (колесо после клика по карте, кнопки), панели
  команды и инженера, палитра следует теме.
- Риски: фильтры и карточки с разбором; KPI, план и профили переоформлены:
  таблицы, строки «подпись — значение», подписи с заглавной буквы.
- Состояние API — иконка; время расчёта плана и время ответа API показаны отдельно.

### Безопасность и доступ
- Вход по токену и три роли (`viewer`, `planner`, `admin`); пользователи —
  `tools/manage_users.py`; журнал действий `audit_log`; ограничение подбора токена.
- Раздача статики не позволяет выйти за пределы каталога фронта; заголовки
  безопасности и CSP отдаёт приложение.
- `/api/health` и `/api/version` без токена отдают минимум информации.

### Эксплуатация
- GitLab CI: юнит-тесты, PostgreSQL-тесты, полный цикл квартала с нулём ошибок
  приёмки, сверка чистой установки с обновлением миграциями, сборка фронта и
  свежесть `web/dist`.
- Docker Compose: PostgreSQL, приложение, Caddy, Prometheus, Grafana, резервные
  копии с проверкой восстановления.
- Числа в README генерирует `tools/readme_numbers.py`.

### Обновление и совместимость
- Примените миграции: `docker compose run --rm migrate`. `db/06_migration_stamps.sql`
  содержит отметки для чистой установки; тома PostgreSQL, созданные из прежних
  файлов `db/*.sql`, пересоздайте (`docker compose down -v`) или обновите миграциями
  (`docs/RUNBOOK.md`, раздел 4).
- Задайте `PI_PLANNER_ADMIN_TOKEN` в `.env`: без него `docker compose` не стартует;
  `run.sh` создаёт токен сам. Для доверенной машины — `PI_PLANNER_AUTH=off`.
- Формат файла факта: колонка `completed_sp`, явные числа часов (в том числе 0),
  подтверждение «отчёт полный». Файлы `demo/*.csv` соответствуют этому формату.
- Автоматическое переигрывание более поздних отчётов после исправления прошлого и
  доказательство глобального оптимума плана не реализованы.
